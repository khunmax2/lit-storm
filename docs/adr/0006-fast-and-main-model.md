# โมเดลเร็วสำหรับค้นคว้า โมเดลหลักสำหรับเขียน

รุ่นแรกใช้โมเดลที่ผู้ใช้เลือกตัวเดียวกับทุกขั้นของ Run (web-app-design.md, การเลือก LLM) รุ่นสองกลับมาแยกเป็น 2 บทบาท คือ **โมเดลหลัก** ใช้เขียนโครงร่าง บทความ และขัดเกลา ส่วน**โมเดลเร็ว** ใช้ในขั้นค้นคว้า เช่น การตั้งคำถาม การจำลองผู้เชี่ยวชาญ การตั้งคำค้น ผู้ใช้ยังเลือกแค่โมเดลหลักตามเดิม ส่วนโมเดลเร็วผู้ดูแลตั้งครั้งเดียวทั้งระบบ

เหตุผลคือเวลา ขั้นค้นคว้าเรียก LLM หลายสิบครั้งต่อ Run แต่ละครั้งเป็นคำตอบสั้นที่ไม่ต้องการโมเดลที่เขียนเก่ง ขณะที่ขั้นเขียนเรียกไม่กี่ครั้งแต่คุณภาพของรายงานมาจากตรงนั้น รุ่นสองตั้งเป้าเวลาไว้ที่ ≤ 2 / 5 / 12 นาทีตามระดับความลึก และขั้นค้นคว้าเป็นส่วนที่กินเวลามากที่สุด ระบบ Streamlit เดิมก็แยก 2 บทบาทนี้ด้วยเหตุผลเดียวกัน

## Considered Options

- **ใช้โมเดลเดียวต่อไป แล้วเร่งด้วยวิธีอื่นอย่างเดียว** ไม่เลือก เพราะการทำงานขนานและแคชลดเวลาได้ แต่ไม่ลดเวลาต่อการเรียกแต่ละครั้ง
- **ให้ผู้ใช้เลือกทั้ง 2 โมเดล** ไม่เลือก เพราะผู้ใช้ส่วนใหญ่ไม่รู้ว่าขั้นไหนต้องการอะไร และกล่องพิมพ์จะรกขึ้นโดยไม่จำเป็น

## Consequences

- เก็บทั้ง 2 โมเดลไว้กับ Run เหมือนที่เก็บโมเดลเดียวในรุ่นแรก และบันทึกค่าใช้จ่ายแยกตามโมเดล (มีอยู่แล้ว)
- ถ้าโมเดลเร็วถูกปิด Run ที่รออยู่เข้าสถานะ `needs_selection` แบบเดียวกับโมเดลหลัก
- Engine ที่ไม่มีการแยกบทบาทในตัว เช่น Deep Research ใช้โมเดลหลักอย่างเดียวได้
- ใช้สคริปต์วัดผลของรุ่นสองยืนยันว่าเร็วขึ้นจริงโดยคุณภาพไม่ตก ถ้าไม่คุ้มให้ถอยกลับเป็นโมเดลเดียวได้ เพราะเป็นการตั้งค่าของผู้ดูแล
