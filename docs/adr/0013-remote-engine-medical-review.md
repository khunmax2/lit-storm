# Engine ระยะไกล: Medical Review เรียก MedicalReviewerAgent ผ่าน REST

แท็บ Medical Review (engine `medical`) ส่งงานให้ MedicalReviewerAgent (MRA) ซึ่งเป็นบริการแยก มี Postgres, Redis, worker, SearXNG สายวิชาการ และเว็บของตัวเอง แล้ว engine ของเราทำหน้าที่เป็น client: ส่งคำถามผ่าน REST, ตามความคืบหน้าผ่าน SSE แล้วแปลงผลเป็น `report.json` ตกลงกับเจ้าของเมื่อ 2026-10-17 (grilling 3 รอบ) หลังพี่เลี้ยงขอให้เพิ่ม MRA และเจ้าของ MRA อนุญาตให้ใช้

## สิ่งที่ตัดสินใจ

1. **ไม่ย้ายโค้ดของ MRA เข้ามา แต่เรียกเป็นบริการ**
   - MRA เป็นระบบเต็มตัว: pipeline LangGraph, คิวและ event ใน Redis, จุดพักใน Postgres, engine ค้นหาวิชาการที่เขียนเอง และหน้า admin 9 หน้า
   - ถ้าย้ายเข้ามาจะต้องตามแก้ทุกครั้งที่ MRA อัปเดต และเสียคุณค่าของ repo ต้นทาง เหมือนที่ตัดสินใจไว้กับ STORM, Deep และ Agent
   - เราจึงเพิ่ม "engine ระยะไกล" (`catalog.remote`) ใช้สัญญาเดียวกับ engine อื่น (ADR-0004) ส่วนอื่นของระบบ เช่น คิว, โควตา, หน้า Run, รายงาน, export และ MCP จึงไม่ต้องรู้ว่างานทำที่ไหน
2. **DeepLit รู้แค่ที่อยู่กับ API key**
   - `system_settings["medical"]` เก็บ `url` ที่ server ใช้ (Caddy ของ MRA ซึ่งให้บริการทั้ง `/api/v1` และ `/r/{id}`), `web_url` ที่คนใช้เปิด (ไม่บังคับ) และ key ที่เข้ารหัสไว้
   - โมเดล แหล่งค้น ขีดจำกัด และอภิธานศัพท์ตั้งที่หน้า admin ของ MRA เท่านั้น ไม่ลอกมาไว้สองที่
   - แท็บแสดงเมื่อตั้งครบทั้งที่อยู่และ key (`modes.offered`)
3. **Run ยังบันทึกโมเดลกับ Search Provider ค่าเริ่มต้นไว้** เพราะคอลัมน์เป็น not null แต่ engine ไม่ใช้
   - การ์ดแสดงเป็น "MedicalReviewerAgent / MRA" แทน
   - Run ไม่ถูกพักเมื่อผู้ดูแลปิดโมเดลหรือแหล่งค้นนั้น (`park_unavailable`)
   - ถ้าในอนาคตมี engine ระยะไกลหลายตัว ค่อยพิจารณาให้สองคอลัมน์นี้เป็น null ได้
4. **สิ่งที่ engine ระยะไกลเพิ่มให้ทั้งระบบ:**
   - **ค่าใช้จ่าย:** usage event มี `usd` ได้ คือค่าใช้จ่ายที่บริการคิดมาแล้ว (`cost.paid`)
   - **คืนโควตาเมื่อได้ผลฟรี:** โน้ต `service_cache` บอกว่า MRA ให้รีวิวเดิมที่ทำไว้ภายใน 24 ชั่วโมง จึงคืนโควตาแม้ Run สำเร็จ
   - **เหตุผลใหม่ 2 ข้อ คืนโควตาทั้งคู่:**
     - `service_unavailable`: ติดต่อไม่ได้ หรือมีงานรอนานเกินเวลาของ Run
     - `service_declined`: บริการไม่รับคำถาม เช่น เหตุฉุกเฉิน หรือคำถามเฉพาะตัวคนไข้ แสดงข้อความของ MRA พร้อมสายด่วน
   - **key ของบริการ:** ส่งถึง process ของ Run ผ่าน `Secrets.service_api_key` เหมือน key อื่น
5. **ยกเลิกที่ MRA เฉพาะเมื่อไม่มี Run อื่นใช้รีวิวนั้น**
   - MRA ให้รีวิวเดียวกับคำถามซ้ำภายในวัน ถ้า A ยกเลิกแล้วงานของ B หายไปด้วยจะผิด
   - Worker ตรวจแล้วจึงส่ง `DELETE` (`medical.release`) เพราะ Worker เห็นฐานข้อมูล แต่ process ของ Run ไม่เห็น
6. **รายงาน 2 แบบ**
   - **`report.json`:** คำตอบ, ข้อค้นพบหลักพร้อมระดับความน่าเชื่อถือ, ตารางเปรียบเทียบ, ผลวิเคราะห์รวม, GRADE, ช่องว่างงานวิจัย, วิธีการ (PICO) และงานวิจัยที่รวมไว้
     - paper แต่ละฉบับเป็น Source
     - หลักฐานของแต่ละ Source คือประโยคในบทคัดย่อที่ MRA ใช้ตรวจตัวเลข (`evidence_quote`)
   - **"รายงานแบบเต็ม (MRA)":** หน้าแบบ offline ของ MRA ซึ่งเก็บไว้กับ Run ตอนจบ จึงเปิดได้แม้ MRA จะปิดอยู่ แสดงใน sandbox เหมือนหน้าแบบโต้ตอบ (ADR-0008)
7. **canvas ของ Medical Review วาดจาก event ของ MRA เอง** (โน้ต `medical`) ไม่ใช้ event ภาษากลาง (ตามที่ตกลงว่า canvas ของแต่ละโหมดต้องสะท้อนพฤติกรรมของโหมดนั้น)
   - ขั้นตอน: ตั้งคำถาม → ค้น → คัดกรอง → อ่านและตรวจตัวเลข → สังเคราะห์
   - การ์ดของ paper แต่ละฉบับมีสีตามทิศทางของผล (ทิศทาง ไม่ใช่ดีหรือเสีย) และมีป้ายเมื่อสองโมเดลเห็นไม่ตรงกัน
8. **MCP:**
   - เพิ่มเส้น `deeplit-medical` ที่รับตัวเลือกของ MRA แทนความลึก แหล่งค้น และโมเดล
   - เส้นรวมรับ `mode="medical"`
   - ตัวกันเริ่มซ้ำเทียบตัวเลือกที่ส่งให้ MRA ด้วย เพราะถามเร็วกับรีวิวเต็มของคำถามเดียวกันไม่ใช่งานซ้ำกัน

## ทางเลือกที่ไม่เลือก

- **ย้าย pipeline ของ MRA มาเป็น engine ใน process ของเรา:** ต้องมี Redis กับ SearXNG สายวิชาการอยู่ดี และต้องตามแก้โค้ดของคนอื่นตลอด
- **เชื่อมผ่าน MCP ของ MRA:** MCP ออกแบบมาให้ AI เรียกใช้ ไม่มี event ความคืบหน้าสด และ export ได้น้อยกว่า REST
- **ลอกหน้าตั้งค่าของ MRA มาไว้ใน DeepLit:** ค่าตั้งจะอยู่สองที่และขัดกันได้
- **event ภาษากลางสำหรับทุกโหมด:** ทำให้ canvas หน้าตาเหมือนกันทุกโหมด ประโยชน์ที่เหลือ (ตัวเลขสรุป, canvas พื้นฐาน) ไม่คุ้มแรงตอนนี้ ค่อยทำเมื่อมีโหมดเพิ่มอีกหลายตัว

## Consequences

- การ deploy MRA เป็นงานแยก: ต้องเพิ่ม container ราว 4–5 ตัวบนเครื่องที่รัน (api, worker, Redis, SearXNG, web) ถ้ารันคู่กับ DeepLit ใช้ Postgres ร่วมกันได้ ส่วน DeepLit เปลี่ยนแค่ที่อยู่ในหน้าตั้งค่า
- แท็บใช้งานได้เท่าที่ MRA พร้อม: ถ้า MRA ล่ม แท็บจะแสดงคำเตือน (`GET /api/medical/status` เช็กทุก 30 วินาที) และ Run จบแบบคืนโควตา
- บนเครื่องนี้ MRA อยู่ใน compose project แยก (`mra`) และ DeepLit ติดต่อผ่าน `http://host.docker.internal:8088`
