# การตีความหัวเรื่องเป็นขั้นแรกของทุก Run

หัวเรื่องที่ผู้ใช้พิมพ์มักสั้นเพียงไม่กี่คำ เช่น "ภาษีคาร์บอน" หรือ "Remote work" แต่ละ engine จึงเดาขอบเขตเอาเองระหว่างค้น ส่วนหัวเรื่องภาษาไทยมักได้แต่แหล่งภาษาไทย (ดู [research/2026-10-06-thai-deep-empty-report](../research/2026-10-06-thai-deep-empty-report.md)) ตอนออกแบบแท็บ Medical Review เจ้าของเห็นว่า MRA ตีความคำถามเป็น PICO ก่อนค้น จึงอยากให้ทุกโหมดทำแบบเดียวกัน ตกลงกันเมื่อ 2026-10-17 (grilling Q18–Q23)

## สิ่งที่ตัดสินใจ

1. **ตีความใน process ของ Run เป็นขั้นแรก ("interpret") ไม่ใช่ใน API ตอนส่ง**
   - ผู้ใช้ไม่ต้องรอที่หน้าส่ง ค่าใช้จ่ายบันทึกกับ Run เหมือนขั้นอื่น และการยกเลิกใช้กลไกเดิม
   - กดลองใหม่แล้วตีความใหม่
   - ปุ่มขัดเกลาโจทย์ยังทำงานใน API เหมือนเดิม เพราะต้องรอให้ผู้ใช้ตอบ
2. **ไม่มีขั้นยืนยัน** (Q19 ก)
   - ผู้ใช้เห็นการตีความบนการ์ด Run และในรายงาน ถ้าไม่ตรง ก็แก้หัวเรื่องหรือใช้ปุ่มขัดเกลาแล้วรันใหม่
   - ถ้าพบว่าตีความผิดบ่อย ค่อยเพิ่มปุ่ม "ดูการตีความก่อน" (Q19 ค)
3. **ได้ออกมา 5 ส่วน:** คำถามวิจัยที่ชัดขึ้น, ขอบเขต (เฉพาะที่หัวเรื่องบอกเป็นนัย), ข้อสมมติ, คำค้นภาษาอังกฤษและไทย, และสิ่งที่ไม่รวม
   - คำตอบจากปุ่มขัดเกลาและขอบเขตการค้นของ Project ส่งเข้าไปด้วย การตีความจึงตามสิ่งที่ผู้ใช้บอกไว้แล้ว (Q20)
   - ชื่อรายงานยังเป็นหัวเรื่องตามที่พิมพ์ (Q21)
4. **ส่งต่อให้ engine ผ่าน `instructions.focus` จุดเดียว**
   - เป็นจุดที่คำตอบจากปุ่มขัดเกลาและขอบเขตการค้นใช้อยู่แล้ว ทั้ง STORM, Deep และ Agent Research จึงได้ผลพร้อมกันโดยไม่ต้องแก้ engine ทีละตัว
   - ข้อแลก: engine เห็นคำค้นเป็นข้อความแนะนำ ไม่ได้ค้นด้วยคำนั้นตรง ๆ โมเดลที่เขียนคำค้นของแต่ละ engine เป็นคนเลือกใช้
5. **คำค้นภาษาไทยส่งเฉพาะงานภาษาไทย** (รายงานภาษาไทย หรือหัวเรื่องมีอักษรไทย) ส่วนคำค้นภาษาอังกฤษส่งทุกงาน
   - งานภาษาอังกฤษที่ได้คำค้นภาษาไทยจะดึงแหล่งภาษาไทยมาปน
   - ภาษาที่ใช้จริงบันทึกไว้ใน `searched` หน้าเว็บกับ export จึงแสดงเฉพาะคำค้นที่ใช้
6. **เรียกโมเดลค้นคว้า (fast model) หนึ่งครั้ง** ถ้าไม่ได้ตั้งไว้ ใช้โมเดลของ Run
   - ถ้าโมเดลตอบไม่ได้ หรือคำตอบไม่มีคำถาม Run ทำต่อด้วยหัวเรื่องตามที่พิมพ์ และบันทึกเหตุผลไว้ในโน้ต
   - การตีความไม่เคยทำให้ Run ล้ม
7. **เก็บไว้ 3 ที่:**
   - โน้ต `interpretation` ของ Run (การ์ด Run และ MCP `interpreted_as`)
   - `work/interpretation.json`
   - ฟิลด์ `interpretation` ใน `report.json` เป็นฟิลด์ไม่บังคับ schema ยังเป็น 1 (ADR-0005) หน้ารายงานและ export HTML, Markdown และ PDF แสดงเป็นหัวข้อ "วิธีการ"
8. **ค่าเริ่มต้นเปิด ผู้ดูแลปิดรายโหมดได้** (Q22)
   - Run เก็บค่าตอนสร้างไว้ใน config (`interpret`) การเปลี่ยนค่าจึงไม่กระทบ Run ที่สร้างแล้ว
   - Co-STORM ไม่ตีความ เพราะผู้ใช้กำหนดทิศทางเองในแต่ละ Turn
   - Medical Review ไม่ตีความ เพราะ MRA ตีความเป็น PICO เอง
   - catalog ประกาศว่าโหมดไหนตีความได้ (`interprets`)

## ทางเลือกที่ไม่เลือก

- **ตีความใน API ก่อนเข้าคิว:** ผู้ใช้ต้องรอ 2–5 วินาทีทุกครั้งที่กดส่ง และค่าใช้จ่ายไม่อยู่กับ Run
- **ให้ยืนยันการตีความก่อนค้น:** เพิ่มขั้นตอนทุกครั้ง ทั้งที่ส่วนใหญ่ตีความถูก
- **ใส่คำค้นลงใน engine โดยตรง** (เช่น ให้ STORM ค้นด้วยคำค้นเหล่านี้ก่อน): ได้ผลตรงกว่า แต่ต้องแก้ทั้ง 3 engine และโค้ดของ repo ต้นทาง ค่อยพิจารณาถ้าผลวัดชี้ว่าแบบผ่าน focus ไม่พอ
- **แปลหัวเรื่องเป็นภาษาอังกฤษอย่างเดียว:** ได้แค่ส่วนคำค้น ไม่ได้ขอบเขตกับสิ่งที่ไม่รวม

## ผลที่วัด

วัด 6 หัวเรื่อง (ไทย 3 อังกฤษ 3) × STORM และ Deep ที่ระดับเร็ว เปิดเทียบปิด รวม 24 Run ([benchmarks/2026-10-17-interpretation](../benchmarks/2026-10-17-interpretation.md))

- **STORM:** แหล่งที่ตรงเรื่อง 89% เทียบ 84% และหัวเรื่องไทย 88% เทียบ 79% หัวเรื่องไทยได้แหล่งภาษาอังกฤษมากขึ้น (แหล่งไทยลดจาก 58% เหลือ 29%)
- **Deep:** ตรงเรื่อง 100% ทั้งสองฝั่ง ตัวตัดสินแยกความต่างไม่ได้
- **ขั้นตีความ:** มัธยฐาน 1.8 วินาที ราว 500 token ทุก Run ได้การตีความ ไม่มี Run ล้ม
- **Agent Research:** ยังไม่ได้วัด เพราะต้องใช้งบเพิ่มราว $0.65

จึงเปิดเป็นค่าเริ่มต้นตามที่ตกลงไว้ ถ้าวัด Agent แล้วผลแย่ลง ให้ปิดเฉพาะโหมดนั้นในหน้าโหมดวิจัย

## Consequences

- ทุก Run ของ STORM, Deep และ Agent เพิ่มขึ้น 1 ขั้น ใช้เวลาราว 2–5 วินาที ค่าใช้จ่ายไม่ถึง $0.001
- ผลวัดอยู่ใน [benchmarks/2026-10-17-interpretation](../benchmarks/2026-10-17-interpretation.md)
