# Load test: หลาย Run และหลายคนพร้อมกัน (2026-09-30)

วัดด้วย `server/tests/load_test.py` บน stack แยก `litstorm-load` ที่อยู่หลัง `/litstorm` เหมือนบน host ผลดิบอยู่ใน [2026-09-30-concurrency.json](2026-09-30-concurrency.json)

- **Run:** ใช้ Engine ทดสอบ (`engines/fake.py`) ที่โหลดไลบรารีของ STORM จริง เดินครบ 4 stage และส่ง progress note ทุก 2 วินาที แต่ไม่เรียก LLM หรือการค้นหา จึงไม่เสียเงิน
- **ผู้ใช้:** ทุกคน poll หน้าเว็บแบบเดียวกับหน้า Run จริง ได้แก่ events ทุก 2.5 วินาที, Session ทุก 4 วินาที และ sidebar ทุก 15 วินาที
- **เครื่อง:** เครื่อง dev 16 core ที่ Docker เห็น RAM 15.3 GB ตัวยิงโหลดรันบนเครื่องเดียวกัน จึงแย่ง CPU กับ stack ด้วย

- **แบบสุดท้ายรันกับ API 2 process** แบบอื่นรันกับ API process เดียว
- **เข้าคิวเร็ว:** ผู้ใช้ 100 คนส่ง 200 Run พร้อมกัน เข้าคิวครบใน 2.7 วินาที
- **ลำดับยุติธรรม:** ไม่มี Run ที่สองของใครเริ่มก่อนที่ทุกคนได้ Run แรก
- **RAM ต่อ Run:** ใช้ค่าที่ container รายงาน ราว 275 MB ถ้า embed ผ่านบริการ และราว 520 MB ถ้าใช้โมเดลในตัวในช่วงที่โหลด torch
  - RSS ต่อ process ออกมา 330 และ 610 MB เพราะนับหน้าไลบรารีที่ process ใช้ร่วมกันซ้ำ
- **Worker ขณะว่าง:** 60–320 MB ขึ้นกับว่ามี process สำรอง (Spare) อยู่หรือไม่
- **จำนวน connection ของ DB:** สูงสุด 59 เส้น ในแบบที่ใช้ API 2 process

## สิ่งที่พบและแก้ในรอบนี้

1. **ผู้ใช้ 100 คนส่งงานพร้อมกันแล้วได้ 500**
   - อาการ: `QueuePool limit ... timed out`
   - สาเหตุ: FastAPI รัน dependency แบบ sync, handler และการตรวจ response เป็นงานแยกบน thread pool เดียวกัน (40 thread) ขณะที่คำขอยังถือ connection อยู่ระหว่างงานเหล่านั้น เมื่อมีคำขอมากกว่า connection บวก thread ก็ติดตายรอกันเองจนครบ 30 วินาทีของ pool
   - ลองแก้ครั้งแรกด้วยการคืน connection หลังอ่านผู้ใช้ ยังเหลือ 500 อยู่ 6 ครั้ง เพราะการตรวจ response ก็ขอ thread อีกรอบขณะที่ถือ connection
   - วิธีที่ใช้: `api/deps.py` ให้คำขอใช้ DB พร้อมกันได้ไม่เกินจำนวน connection ของ pool คำขอที่เกินจะรอบน event loop โดยไม่ถือทั้ง thread และ connection
   - มีเทสต์ `test_more_requests_than_connections_wait_their_turn` ที่ตอบ 500 กับโค้ดเดิมและผ่านกับโค้ดใหม่
   - pool ขยายจาก 5+10 เป็น 10+20 เส้นต่อ process
2. **API ช้าเมื่อผู้ใช้ 100 คนดูงานสดพร้อมกัน (ราว 70 คำขอต่อวินาที)**
   - API process เดียวใช้ CPU เฉลี่ย 78% ของ core และพุ่งเกิน 100%
   - p50 ขึ้นเป็น 225 ms และ p95 เป็น 1.6 วินาที
   - แก้ด้วยการรัน uvicorn 2 process (`LITSTORM_API_WORKERS`) และให้ Postgres รับได้ 200 connection
   - ผล: p50 เหลือ 27 ms, p95 เหลือ 613 ms และรับคำขอได้มากขึ้น 24%
3. **Run ใช้ RAM เกินจำเป็น:** ไลบรารีของ STORM ดึง torch เข้ามาตั้งแต่ import (`langchain_text_splitters` import transformers และ `lm.py` import `AutoTokenizer`)
   - ทำให้ process ใช้ 614 MB ตั้งแต่ก่อนเริ่มงาน
   - แก้ให้โหลด torch เฉพาะตอนใช้ embedding ในตัว เหลือ 347 MB
   - process สำรอง (Spare) ไม่โหลด torch ล่วงหน้าแล้ว Run ที่ใช้โมเดลในตัวจึงช้าลงราว 4.6 วินาทีที่ขั้นเขียน
4. **Run หลายตัวเริ่มพร้อมกันแล้วกิน CPU ทุก core:** ตอนโหลดไลบรารี process ของ Run จึงตั้ง nice 10 ให้ API กับ DB ได้ CPU ก่อน

## ข้อจำกัดของการวัด

- **Engine ทดสอบไม่ได้เรียกบริการภายนอก:** เมื่อรันจริงหลาย Run พร้อมกัน ข้อจำกัดที่มาถึงก่อน RAM คือ Search Provider โดย SearXNG ที่ดึงผลจาก search engine ภายนอกเองจะติด CAPTCHA ตามด้วย rate limit ของบัญชี LLM
- **ตัวยิงโหลดแย่ง CPU กับ stack:** ช่วงที่ 20 process โหลดไลบรารีพร้อมกัน เวลาตอบของ API ที่วัดได้จึงรวมเวลาที่ตัวยิงโหลดเองรอ CPU ด้วย
