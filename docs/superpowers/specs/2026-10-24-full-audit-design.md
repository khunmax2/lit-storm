# ตรวจ DeepLit ทั้งระบบ — การออกแบบ

วันที่ 2026-10-24 · ผู้สั่ง: เจ้าของโปรเจกต์ · คุยกันใน session เดียวกับงานหน้าสถานะระบบและหน้า login ใหม่

## ทำไม

เจ้าของอยากกวาดหา "ของที่ซ่อนอยู่" ก่อนที่ผู้ใช้จะเจอเอง ได้แก่:
- บั๊กที่แอบแฝง
- ช่องโหว่ด้านความปลอดภัย
- จุดที่ UX/UI ใช้แล้วติดขัดหรือดูไม่ดี

ไม่ได้มีเหตุการณ์เฉพาะที่ทำให้กังวล เป็นการตรวจเชิงป้องกันก่อนรอบขึ้น 203 ถัดไป

## เป้าหมาย

1. ตรวจทุกด้านของ DeepLit แล้วได้ **รายงานสิ่งที่เจอ** ที่เจ้าของอ่านแล้วตัดสินใจได้ทันทีว่าจะให้แก้ข้อไหน
2. หลังเจ้าของเลือกแล้ว แก้ข้อที่เลือก โดยแต่ละข้อมีเทสต์ที่พิสูจน์ว่าแก้แล้วจริง

## สิ่งที่ไม่ทำ (non-goals)

- ไม่แก้โค้ดของ MedicalReviewerAgent (repo ของคนอื่น) ตรวจเฉพาะจุดที่ DeepLit เชื่อมกับมัน ถ้าเจอปัญหาใน MRA ให้จดไว้ในรายงานเป็นข้อแนะนำ
- ไม่แตะเครื่อง 203, GitLab ของ NECTEC และไม่ deploy
- ไม่เพิ่มฟีเจอร์ใหม่ และไม่ออกแบบหน้าจอใหม่ นอกจากที่จำเป็นต่อการแก้ข้อที่เจอ
- ไม่อัปเกรด dependency ข้ามรุ่นหลัก เว้นแต่เป็นการปิดช่องโหว่ที่ยืนยันแล้ว

## สิ่งที่ถือว่าล้มเหลว แม้จะทำงานได้ (anti-goals)

- **แก้โดยไม่ถาม:** แก้สิ่งที่ผู้ใช้จะเห็นความเปลี่ยนแปลง (ย้ายปุ่ม, เปลี่ยนข้อความ, เปลี่ยนขั้นตอน) ก่อนเจ้าของอนุมัติ
- **รายงานรก:** รายงานเต็มไปด้วยข้อจุกจิกจนข้อสำคัญจม ต้องจัดลำดับ และรวมข้อเล็กไว้ท้าย
- **ข้อที่ไม่มีหลักฐาน:** รายงานข้อที่ไม่ได้ยืนยันจริง ทุกข้อต้องมีหลักฐาน เช่น ตำแหน่งในโค้ด, ขั้นตอนทำซ้ำ, ภาพหน้าจอ หรือเทสต์ที่ล้ม
- **ใช้งบเกิน:** ค่า OpenRouter รวมเกิน **$3**
- **ทำร้ายข้อมูลจริง:** แตะข้อมูลของ production หรือเผยแพร่ key หรือ token

## ข้อจำกัด

- **ที่ตรวจ:** ทำในเครื่องเท่านั้น Docker Desktop ใช้ร่วมกับ MRA จึงห้าม restart Docker เอง (ดูรายละเอียดใน "การตัดสินใจของผู้ลงมือ" ข้อ 1)
- **ฐานที่ตรวจ:** branch ใหม่ `audit/2026-10-24` ที่รวม `main` + `feat/system-monitor` + `feat/login-redesign` ไว้ในเครื่อง (ไม่ push) เพื่อตรวจของที่จะขึ้นจริงรอบหน้า
- **key ของ OpenRouter:** อ่านจาก `stack/.env` ส่งผ่าน stdin เท่านั้น ห้ามพิมพ์ออกจอหรือใส่ใน command line
- **บัญชีทดสอบ:** สร้างผ่าน script ในฐานข้อมูลของเครื่อง (`*@test.local`) ห้ามพิมพ์รหัสผ่านในเบราว์เซอร์ ลบออกเมื่อเสร็จ
- **ห้าม commit:** `stack/secrets/`, `*.env`, `host.env`
- **commit:** ลงท้ายด้วย `Co-Authored-By: Claude Opus 5.5 (1M context) <noreply@anthropic.com>` และ push เฉพาะเมื่อเจ้าของสั่ง

## ตรวจอะไร และอย่างไร

### 1. ความปลอดภัย

- **สิทธิ์ทุก route:** เขียนเทสต์อัตโนมัติไล่ทุก endpoint ใน `/api` ว่าใครเรียกได้ คือ ไม่ได้ login, ผู้ใช้ทั่วไป, ผู้ใช้อื่น (IDOR), ผู้ดูแล และ token ของ MCP แต่ละ scope เทียบกับที่ควรเป็น และเก็บเทสต์นี้ไว้ในชุดเทสต์ถาวร
- **การ login:** session, CSRF, ลิงก์ตั้งรหัสผ่าน, การปิดหรือลบบัญชี, การเดารหัสผ่านซ้ำๆ (มีการจำกัดไหม)
- **SSRF:** ทุกจุดที่ผู้ดูแลหรือผู้ใช้กำหนด URL ได้ เช่น ที่อยู่ของบริการค้นหา, `api_base` ของ openai-compatible, ที่อยู่ของ MRA และลิงก์แหล่งข้อมูลในรายงาน
- **XSS:** ทุกจุดที่แสดง HTML หรือ markdown จากโมเดลหรือจากภายนอก (`dangerouslySetInnerHTML`, หน้า interactive, service page, observatory, export) และตรวจ CSP กับ sandbox
- **ไฟล์และ export:** path traversal ใน `runs_dir`, token ของลิงก์ export และอายุของลิงก์
- **ความลับ:** การเข้ารหัส key ที่เก็บ, log หรือข้อความ error ที่อาจมี key ติดออกไป (รวมหน้าสถานะระบบ)
- **dependency:** `npm audit`, `pip-audit` (หรือเทียบเท่า) เฉพาะช่องโหว่ที่กระทบจริง
- **container และ compose:** สิทธิ์ของ container, พอร์ตที่เปิด, secrets และ HTTP security headers หลัง nginx

### 2. บั๊ก

- **เทสต์และเครื่องมือตรวจโค้ด:** รันเทสต์ทั้งชุด, type check และ lint
- **อ่านโค้ดส่วนเสี่ยง:**
  - คิวและ lease ของ worker, การยกเลิกงาน, timeout
  - โควตา: จอง, คืน และนับข้ามเดือน
  - ถังขยะและการลบถาวร, Co-STORM Turn, สิทธิ์ของ integration account
  - ส่วนที่เพิ่งทำ: หน้าสถานะระบบ, การจัดประเภทความล้มเหลว, การลบบัญชี
- **ลองจริงทุกโหมด** ในงบ $3: STORM, Co-STORM, Deep, Agent และ Medical Review อย่างละอย่างน้อยหนึ่งรอบ ทั้งภาษาไทยและอังกฤษ พร้อม export ทุกรูปแบบ และ MCP
- **จำลองความล้มเหลว:** OpenRouter ตอบ 429, key ผิด, worker ถูกหยุดกลางงาน, MRA ปิด, บริการค้นหาไม่ตอบ แล้วดูว่าผู้ใช้เห็นอะไร หน้าสถานะระบบเห็นอะไร และโควตาคืนถูกไหม
- **ข้อจำกัดของระบบ:** งานพร้อมกันเกินขีดจำกัด, คิวเต็ม, ข้อมูลยาวผิดปกติ (หัวข้อยาวมาก, ภาษาผสม, อักขระพิเศษ)
- **migration:** ขึ้นและลงได้ครบทุกตัว และ backup แล้ว restore ได้

### 3. UX/UI

- **ถ่ายภาพหน้าจอทุกหน้า:** จอคอม 1440, จอ 1024, มือถือ 390, โหมดสว่างและมืด, ไทยและอังกฤษ ในสถานะต่างๆ (ว่าง, กำลังโหลด, error, มีข้อมูลมาก)
- **ไล่ flow ที่ผู้ใช้ทำจริง:**
  - ตั้งค่าครั้งแรก → เชิญผู้ใช้ → ตั้งรหัสผ่าน → รันงานทุกโหมด
  - Co-STORM คุยหลาย Turn
  - export, ย้ายงานเข้าโปรเจกต์, ถังขยะ
  - ตั้งค่าทุกหน้า, หน้าสถานะระบบ, การเชื่อม MCP
- **ตรวจ:** ข้อความที่ยังไม่แปลหรือแปลปนกัน, ปุ่มที่ไม่บอกผล, error ที่ผู้ใช้อ่านไม่เข้าใจ, ความสม่ำเสมอของหน้าตา, การรองรับคีย์บอร์ดและ screen reader ขั้นพื้นฐาน (label, contrast, focus)
- **เกณฑ์อ้างอิง:** heuristic ของ Nielsen และ WCAG 2.2 ระดับ AA ในส่วนที่ตรวจได้จากภาพและ DOM

### 4. ความทนทานและการดูแลระบบ

- health check, log, การ restart, backup cron ตามคู่มือ HOST-203 และการตั้งค่าที่ต่างกันระหว่างเครื่องเรากับ 203 (เทียบจากคู่มือ ไม่เข้าไปที่เครื่อง)

### 5. คุณภาพโค้ด

- โค้ดที่ไม่ได้ใช้แล้ว, เอกสารที่ไม่ตรงกับโค้ด และ TODO ที่ค้าง จดไว้เป็นข้อเล็กท้ายรายงาน

## สิ่งที่เจ้าของจะได้

**รายงาน** `docs/reports/2026-10-24-full-audit.md` และสรุป 10 ข้อสำคัญในแชท แต่ละข้อมี:

| ช่อง | ความหมาย |
|---|---|
| รหัส | เช่น SEC-03, BUG-07, UX-12 |
| ระดับ | **วิกฤต** (ข้อมูลรั่วหรือระบบใช้ไม่ได้) / **สูง** (กระทบผู้ใช้จริงบ่อย หรือช่องโหว่ที่ต้องมีสิทธิ์บางอย่าง) / **กลาง** / **ต่ำ** |
| หลักฐาน | ตำแหน่งในโค้ด, ขั้นตอนทำซ้ำ, ภาพหน้าจอ หรือเทสต์ |
| ผู้ใช้เห็นไหม | ใช่หรือไม่ (ข้อที่ใช่ต้องได้อนุมัติก่อนแก้) |
| วิธีแก้ที่เสนอ | และขนาดงานโดยประมาณ |

**หลังเจ้าของเลือก:** แก้เป็นชุด แต่ละข้อมีเทสต์ที่ล้มก่อนแก้และผ่านหลังแก้ และ commit แยกตามเรื่อง

**ข้อยกเว้นที่ผมตัดสินเอง:** ช่องโหว่ระดับวิกฤตที่ผู้ใช้ไม่เห็นความเปลี่ยนแปลง (เช่น ปิดรูรั่วของข้อมูล) จะแจ้งทันทีที่เจอ แต่ยังรออนุมัติก่อนแก้เหมือนข้ออื่น เพราะเจ้าของต้องการเห็นก่อน

## การตัดสินใจของผู้ลงมือ (Claude ตัดสินเอง หลังผู้ตรวจเอกสารถาม)

ทุกข้อในส่วนนี้เป็นการตัดสินใจของ Claude ไม่ใช่สิ่งที่เจ้าของสั่ง เจ้าของแย้งได้ทุกข้อ

1. **ตรวจบน stack แยกที่ทิ้งได้:**
   - ใช้ compose project ใหม่ `litstorm-audit` ที่พอร์ต 8096 พร้อม volume ใหม่ทั้งหมด
   - ไม่แตะ `litstorm` ที่ :8095 ซึ่งเป็นข้อมูลทดสอบของเจ้าของ และไม่ใช่สำเนาของ production
   - ฐานข้อมูลว่างเปล่า จึงลองตั้งค่าครั้งแรก, migration ขึ้นลง, backup/restore, ลบถาวร และคิวเต็มได้โดยไม่กระทบอะไร ลบทิ้งเมื่อเสร็จ
   - หมายเหตุ: stack `litstorm` ที่ :8095 ตอนนี้รัน api จาก `feat/system-monitor` และฐานข้อมูลอยู่ที่ migration `0014` แล้ว ถ้าจะกลับไปรันโค้ดของ `main` ต้อง downgrade ก่อน (ลองแล้ว ใช้ได้)
2. **รหัสผ่านในเบราว์เซอร์:** กฎเดิมห้ามพิมพ์รหัสผ่านจริงลงในเบราว์เซอร์ของ session และกันไม่ให้ลิงก์หรือ key หลุดในภาพหน้าจอ
   - บน stack แยกที่ทิ้งได้ Playwright จะกรอก **รหัสผ่านทดสอบที่สร้างขึ้นใหม่** ได้ เพื่อลอง flow login, ตั้งรหัสผ่าน, รหัสตั้งต้น และการเดารหัสผิดซ้ำๆ
   - ภาพหน้าจอต้องไม่มีรหัส ลิงก์ หรือ token ติดอยู่ และบัญชีที่สร้างผ่านหน้าเว็บใช้ `*@test.local`
3. **branch:**
   - ทั้งรายงาน การแก้ และเทสต์สิทธิ์ถาวรลงบน `audit/2026-10-24`
   - เจ้าของต้องการรวมทุกอย่างขึ้น 203 ทีเดียวอยู่แล้ว จึงไม่จำเป็นต้องให้สอง feature ขึ้นแยกกัน
   - เมื่อเจ้าของอนุมัติ branch นี้รวมเข้า main ทั้งก้อน
   - งานรอบสองของหน้าสถานะระบบ (เช็กสุขภาพ, แจ้งเตือนออกนอกระบบ) เริ่มหลังจากนั้น
4. **เวลา:** เจ้าของไม่ได้กำหนดเส้นตาย จึงตรวจครบทุกด้าน
   - ภาพหน้าจอถ่ายทุกหน้า ในทุกขนาดจอ ธีม และภาษา
   - สถานะว่าง/โหลด/error ถ่ายเฉพาะหน้าที่มีสถานะนั้นจริง
5. **งบ $3 รวมทุกอย่าง:** รวมค่าที่ MRA ใช้ด้วย
   - วัดจากยอดใช้ของ key ใน OpenRouter ก่อนและหลัง (ผ่าน API ของ OpenRouter โดยไม่พิมพ์ key) ทั้ง key ของ DeepLit และของ MRA
   - Medical Review จำกัดที่ถามเร็ว 1 ครั้ง และรีวิวเต็ม 1 ครั้ง
   - หยุดลองจริงทันทีเมื่อยอดรวมแตะ $2.50
6. **เส้นทาง Agenta (`compose.agenta.yml`, network `agenta-mcp`):** ตรวจจากไฟล์ config เท่านั้น ว่าเปิดอะไรให้ network นั้นเห็นบ้าง ไม่เข้าไปแตะ stack ของ Agenta ส่วน MCP ลองผ่าน `/api/mcp` ของ stack แยก
7. **ตารางสิทธิ์ของแต่ละ endpoint:**
   - ร่างจาก `docs/CONTEXT.md`, `docs/web-app-design.md`, ADR และโค้ด
   - ช่องที่เอกสารไม่ชัด ไม่ใส่ลงเทสต์ถาวร แต่ลงรายงานเป็น "ต้องให้เจ้าของตัดสิน" เพื่อไม่ให้บั๊กที่มีอยู่ถูกล็อกว่าถูกต้อง
   - ช่องที่ชัดแล้วใส่ลงเทสต์

## ส่วนที่ผู้ลงมือตัดสินเอง

- ลำดับการตรวจ การแบ่งงานให้ผู้ช่วยหลายตัวทำขนานกัน และเครื่องมือที่ใช้
  - skill ที่จะใช้: superpowers ได้แก่ dispatching-parallel-agents, systematic-debugging, test-driven-development, verification-before-completion รวมถึง security-review, code-review, ui-ux-pro-max และ Playwright
- การกระจายงบ $3 ระหว่างโหมดต่างๆ
- ข้อไหนเป็นแค่ข้อเล็กที่รวมไว้ท้ายรายงาน
