# Web App Design — บันทึกการออกแบบ

## ข้อสรุปที่ยืนยันแล้ว

### 2026-09-23 — ขอบเขต Project รุ่นแรก

- ใช้ Project ส่วนตัว โดยแต่ละ Project มีผู้ใช้หนึ่งคนเป็นเจ้าของ
- มีบทบาทผู้ใช้และผู้ดูแล
- ยังไม่รองรับสมาชิกหลายคนทำงานร่วมกันใน Project เดียวในรุ่นแรก
- เหตุผล: เริ่มจากขอบเขต ownership และสิทธิ์ที่เรียบง่าย ก่อนเพิ่มความสามารถทำงานร่วมกัน

### 2026-09-23 — ขอบเขต Engine รุ่นแรก

- เปิดใช้งาน STORM แบบสร้างรายงานอัตโนมัติในรุ่นแรก
- แต่ละ Run ทำตั้งแต่ค้นคว้าจนได้รายงานจบในครั้งเดียว โดยไม่หยุดรอผู้ใช้อนุมัติหรือแก้โครงร่างกลางทาง
- ผู้ใช้ติดตามขั้นตอนและยกเลิกงานได้ หากต้องการเปลี่ยนทิศทางให้ปรับโจทย์แล้วสร้าง Run ใหม่
- การหยุดตรวจและแก้โครงร่างกลางทางเป็นแนวทางต่อยอด ยังไม่ได้กำหนดรุ่นที่จะรองรับ
- เตรียมขอบเขตการเชื่อมต่อ engine ให้เพิ่ม Co-STORM ภายหลังได้
- ยังไม่เปิดใช้งาน Co-STORM ในรุ่นแรก และยังไม่กำหนดรายละเอียดการสนทนาแบบโต้ตอบ
- เหตุผล: Co-STORM ต้องจัดการสถานะการสนทนา การรับข้อความระหว่างทำงาน และการกลับมาทำต่อ ซึ่งเพิ่มขอบเขตของ Research Session

### 2026-09-23 — Research Session และประวัติการรัน

- Project มี Research Session สำหรับแต่ละหัวข้อวิจัย
- ผู้ใช้กลับมาปรับโจทย์หรือขอบเขตของ Session เดิมแล้วสั่งทำวิจัยใหม่ได้
- การสั่งทำใหม่สร้าง Run ใหม่ใน Session เดิม เก็บโจทย์และผลลัพธ์แยกตาม Run
- ไม่เขียนทับรายงานจาก Run ก่อน เพื่อให้เปรียบเทียบผลและย้อนดูโจทย์ที่ใช้สร้างรายงานได้
- การ retry คำขออัตโนมัติอยู่ใน Run เดิม ส่วนผู้ใช้กดลองใหม่หลังงานล้มเหลวสร้าง Run ใหม่ตามนโยบายด้านล่าง

### 2026-09-23 — การใช้งานรายงานรุ่นแรก

- ผู้ใช้อ่านรายงาน สำรวจแหล่งอ้างอิง และ export ผลลัพธ์ได้
- ยังไม่รองรับการแก้ไขเนื้อหารายงานบนเว็บในรุ่นแรก
- Interactive Reports เน้นการอ่าน การนำทางตามหัวข้อ และการเปิดดูแหล่งอ้างอิงหรือหลักฐานที่เกี่ยวข้อง
- เหตุผล: การแก้เนื้อหาต้องจัดการประวัติการแก้ไขและความสอดคล้องระหว่างข้อความใหม่กับแหล่งอ้างอิง
- รุ่นแรกรองรับ export เป็น HTML, Markdown และ PDF ตามขอบเขตหลักฐานและ Source Explorer ด้านล่าง

### 2026-09-23 — แหล่งข้อมูลและ Search Provider

- ใช้แหล่งข้อมูลที่ค้นหาผ่าน search engine ได้เป็นค่าเริ่มต้น
- รองรับการเพิ่ม Search Provider โดยผู้ใช้ยกตัวอย่าง Tavily, arXiv และ SearXNG
- ผู้ดูแลกำหนด Search Provider ค่าเริ่มต้นได้ โดยยังไม่ได้ระบุชื่อบริการที่จะใช้ในการติดตั้งจริง
- รุ่นแรกใช้ข้อมูลจาก Search Provider เท่านั้น ยังไม่รองรับการอัปโหลด PDF หรือเอกสารส่วนตัว
- การอัปโหลดเอกสารเป็นแนวทางต่อยอด ยังไม่ได้กำหนดรุ่นที่จะรองรับ
- จากโค้ดปัจจุบัน: มี TavilySearchRM และ SearXNG ใน knowledge_storm/rm.py และมี ArxivRM ที่เรียก arXiv โดยตรงใน frontend/demo_light/arxiv_rm.py การมี adapter ยังไม่ใช่การยืนยันว่าเชื่อมต่อบริการจริงได้ในสภาพแวดล้อมที่นำไปใช้งาน

### 2026-09-23 — การจัดการ Search Provider รุ่นแรก

- ผู้ดูแลระบบเพิ่มและตั้งค่า Search Provider รวมถึง API key และ endpoint ส่วนกลาง
- ผู้ใช้เลือกจากรายการ provider ที่ผู้ดูแลเปิดให้ใช้
- รุ่นแรกยังไม่เปิดให้ผู้ใช้เพิ่ม provider หรือตั้งค่า credentials ส่วนตัว
- การเพิ่มบริการชนิดใหม่ต้องมี adapter รองรับก่อน ไม่ใช่เพียงกรอกชื่อบริการและ API key

### 2026-09-23 — จำนวน Search Provider ต่อ Run

- รุ่นแรก: ผู้ใช้เลือกหนึ่ง Search Provider ต่อ Run และเก็บข้อมูลว่า Run นั้นใช้ provider ใด
- เหตุผล: ทำให้พฤติกรรมการค้นหาและค่าใช้จ่ายเข้าใจง่ายในรุ่นแรก
- รุ่นสอง: รองรับการค้นหาผ่านหลาย Search Provider พร้อมกันภายใน Run เดียว
- รายละเอียดรุ่นสองที่ยังต้องออกแบบ: การรวมและจัดอันดับผล การตัดแหล่งข้อมูลซ้ำ งบการค้นหา และพฤติกรรมเมื่อบาง provider ล้มเหลว
- **ปรับเมื่อ 2026-09-30:** รายละเอียดรุ่นสองตัดสินแล้ว ดู "รุ่นสอง: ค้นหลายแหล่งต่อ Run"

### 2026-09-23 — การเลือก LLM

- ผู้ดูแลเพิ่มรายการโมเดล LLM และกำหนดว่าโมเดลใดเปิดให้ผู้ใช้เลือกได้
- ผู้ใช้เลือกตามชื่อโมเดลจากรายการที่เปิดใช้งาน ไม่ใช้โปรไฟล์ประหยัด/สมดุล/คุณภาพสูงตามข้อเสนอเดิม
- ผู้ดูแลกำหนดโมเดล default ได้
- รุ่นแรกใช้ LLM ที่เลือกหนึ่งโมเดลกับทุกขั้นตอนของ Run
- เก็บโมเดลที่เลือกไว้กับ Run เพื่อไม่ให้การเปลี่ยน default ภายหลังกระทบการเลือกโมเดลของงานเดิม
- การเลือกโมเดลแยกแต่ละขั้นตอนเป็นแนวทางต่อยอดที่ผู้ใช้สนใจ ยังไม่ได้กำหนดรุ่นที่จะรองรับ
- โค้ด STORM เดิมแยกการตั้งค่าโมเดลสำหรับการจำลองบทสนทนา การตั้งคำถาม การสร้างโครงร่าง การเขียนบทความ และการขัดเกลาบทความ
- **ปรับเมื่อ 2026-09-30:** รุ่นสองกลับมาใช้ 2 บทบาท ผู้ใช้ยังเลือกแค่โมเดลหลัก (ใช้เขียน) ส่วนโมเดลเร็ว (ใช้คุยค้นข้อมูล) ผู้ดูแลตั้งครั้งเดียวทั้งระบบ ดู [ADR-0006](./adr/0006-fast-and-main-model.md)

### 2026-09-23 — การทำงานเบื้องหลัง

- เมื่อเริ่ม Run แล้ว งานทำต่อเบื้องหลังแม้ผู้ใช้ปิดแท็บหรือออกจากระบบ
- ผู้ใช้กลับมาติดตามสถานะและเปิดผลลัพธ์จาก Dashboard ได้ภายหลัง
- ใช้ Worker และคิวงานแยกจากหน้าเว็บ พร้อมบันทึกสถานะ Run อย่างถาวร
- การปิดหน้าเว็บหรือออกจากระบบไม่ใช่คำสั่งยกเลิกงาน
- ข้อกำหนดให้ทำต่อจนจบไม่ได้หมายถึง retry ไม่จำกัดเมื่อเกิดข้อผิดพลาด เมื่อ Worker ล่มให้ใช้นโยบายงานถูกขัดจังหวะด้านล่าง

### 2026-09-23 — การ retry คำขอที่ล้มเหลว

- เมื่อคำขอไปยัง LLM หรือ Search Provider ล้มเหลวจากปัญหาชั่วคราว ให้ลองคำขอนั้นซ้ำอัตโนมัติไม่เกิน 2 ครั้งหลังคำขอแรก (รวมไม่เกิน 3 ครั้ง) โดยเว้นระยะเพิ่มขึ้น
- นโยบายนี้เป็นการ retry คำขอภายใน Run เดิม ไม่ใช่การเริ่มงานวิจัยทั้ง Run ใหม่
- เมื่อครบจำนวนครั้งแล้วยังไม่สำเร็จ ให้หยุดงาน แสดงสาเหตุ และเก็บผลส่วนที่ทำสำเร็จไว้
- ข้อผิดพลาดที่ลองซ้ำแล้วไม่ช่วย เช่น API key ไม่ถูกต้อง ให้หยุดทันที
- ข้อควรตรวจตอนพัฒนา: นับ retry รวมกับที่ SDK หรือ engine ทำอยู่แล้ว เพื่อไม่ให้เกิดการลองซ้ำซ้อนเกินขอบเขต
- การเก็บผลบางส่วนไม่ได้รับรองว่าสามารถ resume จากทุกจุดได้ รุ่นแรกเมื่อผู้ใช้สั่งลองใหม่จะเริ่มประมวลผลทั้งรอบ

### 2026-09-23 — การยกเลิก Run

- ผู้ใช้ยกเลิก Run ของตนเองได้ทั้งขณะอยู่ในคิวและขณะทำงาน
- งานที่ยังอยู่ในคิวยกเลิกได้ทันทีโดยไม่เริ่มประมวลผล
- งานที่เริ่มแล้วแสดงสถานะกำลังยกเลิก และหยุดเมื่อถึงจุดที่ปลอดภัย ก่อนเปลี่ยนเป็นยกเลิกแล้ว
- เก็บผลส่วนที่ทำสำเร็จไว้ การยกเลิกไม่ใช่การลบผลลัพธ์
- คำขอที่ส่งไปยังบริการภายนอกแล้วอาจยังมีค่าใช้จ่าย
- รายละเอียดจุดหยุดที่ปลอดภัยและกรณียกเลิกพร้อมกับงานเสร็จต้องกำหนดตอนออกแบบวงจรชีวิตงาน

### 2026-09-23 — จำนวน Run พร้อมกันต่อผู้ใช้

- ค่าเริ่มต้นให้ผู้ใช้แต่ละคนมี Run ที่กำลังทำงานพร้อมกันได้ 1 Run
- งานเพิ่มเติมเข้าคิวรอจนมีช่องประมวลผลว่างตามข้อจำกัดที่เกี่ยวข้อง
- ผู้ดูแลปรับจำนวน Run พร้อมกันต่อผู้ใช้ได้
- เหตุผล: ควบคุมการใช้ทรัพยากรและค่าใช้จ่าย โดยยังให้ผู้ใช้ส่งงานหัวข้อถัดไปรอไว้ได้
- จำนวน Run พร้อมกันต่อผู้ใช้ใช้ค่าเริ่มต้นส่วนกลาง โดยผู้ดูแลตั้งค่าทับ (override) เป็นรายคนได้
- งานรอสูงสุดเริ่มต้น 5 Run ต่อคน รวมงานที่รอเลือกโมเดลหรือ provider ใหม่ ผู้ดูแลปรับได้ และการส่งงานยังต้องมีโควตาเหลือพอ

### 2026-09-23 — เพดาน Run พร้อมกันทั้งระบบ

- ผู้ดูแลกำหนดเพดาน Run ที่ทำงานพร้อมกันทั้งระบบได้
- เริ่ม Run ได้เมื่อไม่เกินทั้งเพดานต่อผู้ใช้และเพดานรวมของระบบ มิฉะนั้นให้งานรอในคิว
- เหตุผล: การจำกัดต่อผู้ใช้อย่างเดียวไม่จำกัดภาระงานรวมเมื่อมีผู้ใช้จำนวนมาก
- สำหรับทดสอบ local กำหนดค่าเริ่มต้นรวมทั้งระบบ 2 Run พร้อมกัน ผู้ดูแลปรับได้ตามกำลังเครื่องและข้อจำกัดบริการ

### 2026-09-23 — การจัดสรรคิวระหว่างผู้ใช้

- เมื่อมีช่องประมวลผลว่าง ให้สลับหยิบงานระหว่างผู้ใช้ที่มีงานรอและยังไม่เต็มเพดานพร้อมกันของตน
- งานของผู้ใช้แต่ละคนเรียงตามเวลาที่ส่ง โดยหยิบงานที่ส่งก่อนก่อน
- การเริ่มงานยังต้องเคารพทั้งเพดานต่อผู้ใช้และเพดานรวมของระบบ
- เหตุผล: ผู้ใช้ที่ส่งงานจำนวนมากไม่ควรครองลำดับคิวจนผู้ใช้อื่นต้องรอครบทุกงาน
- นโยบายนี้จัดสรรโอกาสเริ่มงาน ไม่ได้รับรองเวลาเริ่มหรือเวลาเสร็จเท่ากัน เพราะแต่ละ Run ใช้เวลาต่างกัน

### 2026-09-23 — ผู้ใช้สั่งลองใหม่หลัง Run ล้มเหลว

- ปุ่มลองใหม่สร้าง Run ใหม่ใน Research Session เดิม พร้อมเชื่อมกลับไปยัง Run ที่ล้มเหลว
- คัดลอกโจทย์และค่าที่ใช้จาก Run เดิม และเก็บประวัติ ข้อผิดพลาด และผลลัพธ์ของ Run เดิมไว้
- รุ่นแรกเริ่มประมวลผลใหม่ทั้งรอบ ไม่ resume จากขั้นตอนที่ค้าง
- แยกผลลัพธ์และค่าใช้จ่ายของแต่ละ Run เพื่อให้ตรวจสอบย้อนหลังได้
- การ resume เป็นแนวทางต่อยอดหลังทดสอบการกู้คืนของ engine ยังไม่กำหนดรุ่นที่จะรองรับ
- หากค่าที่คัดลอกอ้างถึงโมเดลหรือ provider ที่ปิดใช้งาน ให้ผู้ใช้เลือกตัวที่เปิดใช้งานก่อนเริ่ม Run ใหม่ ตามนโยบายการปิดบริการด้านล่าง

### 2026-09-23 — Run ถูกขัดจังหวะเมื่อ Worker หรือเครื่องล่ม

- รุ่นแรกตรวจพบและแสดงว่า Run ที่กำลังทำถูกขัดจังหวะ พร้อมเก็บผลบางส่วนที่บันทึกไว้แล้ว
- ไม่เริ่มประมวลผลทั้งรอบใหม่อัตโนมัติ ให้รอผู้ใช้กดลองใหม่ ซึ่งสร้าง Run ใหม่ตามนโยบายเดิม
- เหตุผล: ไม่ให้เกิดค่าใช้จ่ายจากการเริ่มทั้งรอบซ้ำโดยผู้ใช้ไม่ทราบ
- งานที่ยังอยู่ในคิวและยังไม่เริ่มทำสามารถทำต่อเมื่อระบบกลับมา โดยเคารพนโยบายคิวและเพดานพร้อมกัน
- รายละเอียดทางเทคนิคในการตรวจจับ Worker ที่หายไปและป้องกันงานซ้ำยังต้องออกแบบ

### 2026-09-23 — สิทธิ์ผู้ดูแลต่อเนื้อหางานวิจัย

### 2026-09-24 — วงจรชีวิตของ Run

```
queued ──claim──▶ running ──▶ succeeded
  │  ▲              │  ├────▶ failed
  │  │              │  └─lease หมด─▶ interrupted
  │  └─เลือกใหม่─ needs_selection (provider/model ถูกปิด)
  │                 └─ยกเลิก─▶ cancelling ──▶ cancelled
  └─ยกเลิก─▶ cancelled
needs_selection ─ยกเลิก─▶ cancelled
```

- สถานะปลายทางคือ succeeded, failed, cancelled และ interrupted ปุ่มลองใหม่สร้าง Run ใหม่
- เมื่อการยกเลิกชนกับงานเสร็จ ใครเขียนสถานะปลายทางก่อนคนนั้นชนะ ถ้างานเสร็จก่อน ผู้ใช้ได้รายงานและนับโควตาตามปกติ
- ถ้าอยู่ใน cancelling แล้วงานเสร็จพอดี ให้ถือเป็น cancelled แต่เก็บรายงานไว้ให้อ่าน
- การยกเลิกงานที่กำลังทำจะหยุดที่ขอบ stage ถ้าเกิน 30 วินาทีแล้วยังไม่หยุดจะบังคับหยุด และเก็บผลของ stage ที่เสร็จแล้ว
- แต่ละ Run มีเพดานเวลารวม ค่าเริ่มต้น 60 นาที ผู้ดูแลปรับได้ ถ้าเกินจะเป็น failed สาเหตุหมดเวลา

### 2026-09-24 — ความล้มเหลวกับการคืนโควตา

| สาเหตุ | คืนโควตา |
|---|---|
| retry ครบแล้วยังล้มเหลว (timeout, 5xx, rate limit) | คืน |
| API key ไม่ถูกต้อง หรือ credit หมด | คืน |
| Worker ล่ม (interrupted) | คืน |

| ผู้ใช้ยกเลิกหลังเริ่มประมวลผล | ไม่คืน |

- บันทึกค่าใช้จ่ายทุกกรณี: จำนวน token แยกตามโมเดลและจำนวนครั้งที่เรียก search ต่อ stage แสดงเป็นเงิน **โดยประมาณ** ในหน้าการใช้งานของผู้ดูแล

### 2026-09-24 — ค่าที่ผู้ใช้เลือกได้ต่อ Run

- ผู้ใช้เลือกได้แค่หัวข้อ, โมเดล, Search Provider และภาษารายงาน
- ค่าพารามิเตอร์ของ Engine (เช่น จำนวนมุมมองและรอบการสนทนา) ผู้ดูแลตั้งเป็นค่าส่วนกลาง เพราะโควตานับเป็นจำนวน Run ถ้าผู้ใช้ปรับความลึกเองได้ ค่าใช้จ่ายต่อ Run จะต่างกันมาก
- ค่าทั้งหมดที่ใช้จริงเก็บไว้กับ Run
- **ปรับเมื่อ 2026-09-30:** รุ่นสองให้ผู้ใช้เลือกระดับความลึก 3 ระดับ (เร็ว / มาตรฐาน / ลึก) ส่วนตัวเลขเบื้องหลังแต่ละระดับยังเป็นของผู้ดูแล ค่าใช้จ่ายจึงยังมีเพดาน ดู "รุ่นสอง: ระดับความลึก เวลา และความเร็ว"

### 2026-09-24 — บริการที่มีให้ตั้งแต่ติดตั้ง

- ติดตั้ง SearXNG ใน compose และตั้งเป็น Search Provider เริ่มต้น เพื่อให้ส่ง Run แรกได้โดยมีแค่ LLM key ตัวเดียว ส่วน Tavily และ arXiv ผู้ดูแลเปิดเพิ่มได้
- **ปรับเมื่อ 2026-09-30:** SearXNG ยังเป็นค่าเริ่มต้นตามที่เจ้าของโปรเจกต์ต้องการ (ไม่ใช้ Tavily) แต่ปรับตั้งค่าดังนี้
  - **ค้นเว็บทั่วไป:** ค่าตั้งต้นของ SearXNG เปิดแค่ Brave, DuckDuckGo และ Google CSE สองตัวหลังมักติด CAPTCHA หรือถูกระงับ จึงเหลือ Brave ตัวเดียว และ Run ค้นไม่เจออะไรเมื่อ Brave ถูกระงับด้วย เปิด Google, Bing และ Yahoo เพิ่ม (ทดสอบแล้วตอบทั้งไทยและอังกฤษ) SearXNG ส่งทุกคำค้นไปทุก engine ในหมวด การเปิดเพิ่มจึงไม่ลดภาระต่อ engine แต่มีตัวสำรองเมื่อบางตัวถูกระงับ
  - **"SearXNG LDR-academic":** เป็น Search Provider ตัวที่สองที่ระบบสร้างให้ตอนติดตั้ง ชี้ไป SearXNG ตัวเดิมแต่ระบุ engine วิชาการชุดเดียวกับที่ fork `searxng-LDR-academic` เปิด ได้แก่ arXiv, Crossref, Europe PMC, Google Scholar, OpenAIRE, OpenAlex, PDBe, PubMed และ Semantic Scholar
    - engine เหล่านี้อยู่ในหมวด science ซึ่งคำค้นที่ไม่ระบุ engine ไม่เคยใช้ ก่อนหน้านี้จึงเปิดไว้โดยไม่มีผลเลย
    - ไม่ใช้ตัว fork เอง เพราะ engine 2 ตัวที่มีเฉพาะใน fork ใช้ไม่ได้: BASE ตอบว่า "Access denied" กับ IP ที่ไม่ได้ขออนุญาต และ Library of Congress ค้นได้เฉพาะรูปภาพ
    - engine วิชาการแทบไม่มีเนื้อหาภาษาไทย หัวข้อไทยควรใช้ SearXNG แบบค้นเว็บ
- LLM รองรับ Gemini, OpenRouter, Groq, OpenAI และ endpoint ที่เข้ากันได้กับ OpenAI หน้าตั้งค่ามีปุ่มทดสอบการเชื่อมต่อ

  - คลังแหล่งอ้างอิงร่วมใน Project

### รุ่นสอง: กติกาที่ทุก Engine ใช้ร่วมกัน

- ทุก Engine ผ่านคิว โควตา สิทธิ์ ถังขยะ และหน้าอ่านรายงานชุดเดียวกัน
- **รายงาน:** ทุก Engine แปลงผลเป็น `report.json` รูปแบบเดียว ([ADR-0005](./adr/0005-report-json-file.md))
  - Source ที่ไม่มี Evidence แสดงได้ แผงด้านข้างบอกว่าไม่มีข้อความหลักฐาน
  - แสดงชื่อ Engine บนการ์ดของ Run และบนหน้ารายงาน
  - แต่ละ Engine ประกาศขั้นตอนของตัวเองให้แถบความคืบหน้า
- **บริการค้นหา:** แต่ละ Engine ประกาศชนิดที่รองรับ กล่องพิมพ์แสดงเฉพาะบริการที่ใช้กับโหมดนั้นได้ หน้าตั้งค่าบอกว่าบริการไหนใช้กับ Engine ไหน ตัวเชื่อมเพิ่มเติมทำเฉพาะคู่ที่คุ้ม
- **โมเดล:** ปุ่มทดสอบโมเดลตรวจเพิ่มว่าเรียก tool ได้หรือไม่ แล้วบันทึกว่าใช้ได้กับ Engine ไหน กล่องพิมพ์แสดงเฉพาะโมเดลที่ใช้ได้กับโหมดนั้น ผู้ดูแลแก้เองได้
- **โควตา:** 1 Run = 1 หน่วยทุก Engine หน้าการใช้งานแยกค่าใช้จ่ายตาม Engine
- **ขัดเกลาโจทย์:** ขั้นที่เลือกได้ก่อนส่ง Run ใช้ได้ทุกโหมดแบบ batch
  - ระบบถามคำถาม 3–5 ข้อให้โจทย์ชัด ผู้ใช้ตอบหรือข้ามได้
  - ใช้โมเดลที่ผู้ใช้เลือก ไม่หักโควตา
  - มีเพดานต่อคนต่อวัน (ค่าเริ่มต้น 30 ครั้ง ผู้ดูแลปรับได้)
  - คำถามและคำตอบเก็บไว้กับ Run
- **แท็บโหมด:** แสดงเฉพาะโหมดที่ใช้งานได้จริง ผู้ดูแลปิดโหมดได้ในหน้าตั้งค่า ไม่มีแท็บที่กดแล้วใช้ไม่ได้

### รุ่นสอง: ระดับความลึก เวลา และความเร็ว

- ผู้ใช้เลือก**ระดับความลึก**ได้ 3 ระดับ ใช้ชุดเดียวกันทุกโหมด ค่าเริ่มต้นคือมาตรฐาน ผู้ดูแลแก้ตัวเลขเบื้องหลังแต่ละระดับได้ ค่าตั้งต้นมาจากระบบเดิม (`run_options.py`)

| ระดับ | STORM | Co-STORM (ช่วงเตรียม) | Agent Research | Deep Research | เป้าเวลา |
|---|---|---|---|---|---|
| เร็ว | 2 มุมมอง × 2 รอบ | 2 ผู้เชี่ยวชาญ | Iterative 2 รอบ | breadth 2, depth 1 | ≤ 2 นาที |
| มาตรฐาน | 3 × 3 | 3 ผู้เชี่ยวชาญ | Iterative 4 รอบ | breadth 3, depth 2 | ≤ 5 นาที |
| ลึก | 5 × 4 | 4 ผู้เชี่ยวชาญ | โหมด Deep | breadth 4, depth 3 | ≤ 12 นาที |

- เป้าเวลาอ้างอิงจากบริการในตลาด (Perplexity 2–4 นาที, Gemini 5–15, ChatGPT 5–30) เพราะงานที่นานเกินไปผู้ใช้จะไม่ใช้
- **จบอย่างนุ่มนวล:** เมื่อใช้เวลาถึง 80% ของเป้า Engine หยุดค้นเพิ่มแล้วเขียนรายงานจากสิ่งที่มี เพดานเวลารวมของรุ่นแรกยังเป็นตาข่ายสุดท้าย
- **วัดผลก่อนปรับ:** มีสคริปต์วัดผลที่รันหัวข้อชุดเดียวกันทุก Engine ทุกระดับ บันทึกเวลา ค่าใช้จ่าย และจำนวน Source แล้วปรับตัวเลขให้เข้าเป้า
- **วิธีเร่ง** ทำทั้ง 4 ข้อ และวัดผลทีละข้อ
  - โมเดล 2 บทบาท ([ADR-0006](./adr/0006-fast-and-main-model.md))
  - ทำงานขนานมากขึ้น
  - บริการค้นหาที่เร็วเป็นค่าเริ่มต้น: arXiv บังคับเว้น 3 วินาทีต่อครั้ง
  - แคชผลค้นหาภายใน Run และในหัวข้อเดียวกันภายใน 24 ชั่วโมง

### รุ่นสอง: Agent Research และ Deep Research

- **Agent Research** (`khunmax2/lit_agents-deep-research`) import เป็น library ใน subprocess ของ Run
  - ระดับเร็วและมาตรฐานใช้ `IterativeResearcher` ระดับลึกใช้ `DeepResearcher`
  - บริการค้นหาเริ่มจาก SearXNG แล้วเพิ่ม Tavily
  - ต้องใช้โมเดลที่เรียก tool ได้
- **Deep Research** (`khunmax2/lit_deep-research-web`, Nuxt) รันเป็น subprocess ผ่าน **Node CLI** ที่เพิ่มใน fork
  - CLI เรียก `lib/core` ตรง รับ config ทาง stdin ส่ง event ทาง stdout เป็น JSONL
  - key ส่งผ่าน env ของ process นั้น ยกเลิกด้วยการ kill
  - Worker image ต้องมี Node.js
  - บริการค้นหาที่ใช้ได้: SearXNG และ Tavily
  - รายละเอียดใน [ADR-0004](./adr/0004-engine-interface.md)

### รุ่นสอง: Discussion (Co-STORM)

- Discussion เป็น Research Session อีกชนิด หนึ่งหัวข้อเป็นได้ทั้งรายการ Run หรือ Discussion เดียว จึงอยู่ใน Project, ถังขยะ, งานวิจัยทั้งหมด, การค้นหา และเมนูล่าสุดเหมือนหัวข้ออื่น
- **โควตา:** เริ่ม Discussion หัก 1 หน่วย ได้สนทนาสูงสุด 20 Turn (ผู้ดูแลปรับได้) รวมการสร้างรายงาน กด "ต่อเวลา" เพื่อคุยต่ออีกชุดโดยหักอีก 1 หน่วย
- **การทำงาน:** แต่ละ Turn เป็นงานในคิวเดียวกับ Run
  - ได้คิวก่อน Run ใหม่ เพราะผู้ใช้รออยู่ และนับในเพดานงานพร้อมกัน
  - เก็บสถานะของ runner (`CoStormRunner.to_dict()`) หลังจบทุก Turn กลับมาคุยต่อเมื่อไรก็ได้ Discussion ที่เงียบอยู่ไม่กินช่อง
  - Worker ล่มกลาง Turn เสียแค่ Turn นั้น
- **หน้าตา**
  - กลางจอเป็นแชตที่เห็นว่าผู้ใช้ ผู้เชี่ยวชาญแต่ละคน และผู้ดำเนินรายการพูดอะไร พร้อมเลขอ้างอิง
  - ด้านขวาเป็นแผงแผนผังความคิด
  - ปุ่ม: พิมพ์แทรก / คุยต่อ 1 รอบ / ให้คุยเอง 3 รอบ / สร้างรายงาน
  - สร้างรายงานได้หลายครั้ง แต่ละครั้งเก็บเป็นรายงานแยก

### รุ่นสอง: ค้นหลายแหล่งต่อ Run

- เฉพาะ STORM (ใช้ `MultiRM`) เลือกได้สูงสุด 3 แหล่งต่อ Run
- สลับผลจากแต่ละแหล่งทีละรายการ และตัดรายการซ้ำด้วย URL
- งบการค้นหาต่อคำถามแบ่งเท่ากันทุกแหล่ง
- แหล่งที่ล้มถูกข้ามพร้อมบันทึก Run ล้มก็ต่อเมื่อทุกแหล่งล้ม
- นับเป็น 1 Run ตามปกติ

### รุ่นสอง: โครงร่างที่ผู้ใช้กำหนดและ Project

### รุ่นสอง: การติดตั้งและโครงสร้างระบบ

- **ปลายทาง:** host 203.185.144.41 เครื่องเดียวกับ DeepWitya ที่ path **`/litstorm`** หลัง nginx ของ host ซึ่งจัดการ HTTPS (ใบรับรองของ IP ไม่มีโดเมน) ผูกพอร์ตภายในที่ว่าง เช่น `127.0.0.1:10340` stack มี db และ searxng ของตัวเอง
- **ต้องผ่าน 100% บนเครื่อง dev ก่อนขึ้น host:** รุ่นสองทั้งหมดต้องเสร็จและรันได้ทุกอย่างบนเครื่องนี้ก่อน
  - stack บนเครื่องนี้จำลอง host แบบเดียวกับ DeepWitya: nginx ข้างหน้า, path `/litstorm`, origin เดียว, ไม่มี TLS ในเครื่อง
  - dev server ยังอยู่ที่ `/`
- **base path:** ระบบต้องรองรับ base path ที่ตั้งตอน build ได้ ครอบคลุม Vite, router, ตัวเรียก API, path ของ cookie และลิงก์ตั้งรหัสผ่าน
- **image:** GitHub Actions build แล้ว push ขึ้น GHCR เมื่อติด tag host ดึงตาม digest repo และ image เป็น public จึงไม่ต้อง login
- **อีเมล:** ใช้ลิงก์ที่ผู้ดูแลส่งเองไปก่อน แล้วเพิ่ม "ลืมรหัสผ่าน" ผ่านบริการส่งอีเมลเมื่อมีโดเมน
- **สำรองข้อมูล:** ยังไม่ตัดสินวิธี แต่**ต้องตัดสินและทำให้เสร็จก่อนเปิดใช้จริง** สิ่งที่ต้องสำรองคือฐานข้อมูล, ไฟล์ของแต่ละ Run และ `secret_key` ซึ่งต้องเก็บแยกนอกระบบ
