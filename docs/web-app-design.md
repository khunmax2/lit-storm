# Web App Design — บันทึกการออกแบบ

## ข้อสรุปที่ยืนยันแล้ว

### 2026-09-23 — ขอบเขต Project รุ่นแรก

- ใช้ Project ส่วนตัว โดยแต่ละ Project มีผู้ใช้หนึ่งคนเป็นเจ้าของ
- มีบทบาทผู้ใช้และผู้ดูแล
- ยังไม่รองรับสมาชิกหลายคนทำงานร่วมกันใน Project เดียวในรุ่นแรก
- เหตุผล: เริ่มจากขอบเขต ownership และสิทธิ์ที่เรียบง่าย ก่อนเพิ่มความสามารถทำงานร่วมกัน

### 2026-09-23 — ขอบเขต Engine รุ่นแรก

- เปิดใช้งาน STORM แบบสร้างรายงานอัตโนมัติในรุ่นแรก
- แต่ละ Run ทำตั้งแต่ค้นคว้าจนได้รายงานจบในครั้งเดียว โดยไม่หยุดรอผู้ใช้อนุมัติหรือแก้โครงร่างกลางทาง
- ผู้ใช้ติดตามขั้นตอนและยกเลิกงานได้ หากต้องการเปลี่ยนทิศทางให้ปรับโจทย์แล้วสร้าง Run ใหม่
- การหยุดตรวจและแก้โครงร่างกลางทางเป็นแนวทางต่อยอด ยังไม่ได้กำหนดรุ่นที่จะรองรับ
- เตรียมขอบเขตการเชื่อมต่อ engine ให้เพิ่ม Co-STORM ภายหลังได้
- ยังไม่เปิดใช้งาน Co-STORM ในรุ่นแรก และยังไม่กำหนดรายละเอียดการสนทนาแบบโต้ตอบ
- เหตุผล: Co-STORM ต้องจัดการสถานะการสนทนา การรับข้อความระหว่างทำงาน และการกลับมาทำต่อ ซึ่งเพิ่มขอบเขตของ Research Session

### 2026-09-23 — Research Session และประวัติการรัน

- Project มี Research Session สำหรับแต่ละหัวข้อวิจัย
- ผู้ใช้กลับมาปรับโจทย์หรือขอบเขตของ Session เดิมแล้วสั่งทำวิจัยใหม่ได้
- การสั่งทำใหม่สร้าง Run ใหม่ใน Session เดิม เก็บโจทย์และผลลัพธ์แยกตาม Run
- ไม่เขียนทับรายงานจาก Run ก่อน เพื่อให้เปรียบเทียบผลและย้อนดูโจทย์ที่ใช้สร้างรายงานได้
- การ retry คำขออัตโนมัติอยู่ใน Run เดิม ส่วนผู้ใช้กดลองใหม่หลังงานล้มเหลวสร้าง Run ใหม่ตามนโยบายด้านล่าง

### 2026-09-23 — การใช้งานรายงานรุ่นแรก

- ผู้ใช้อ่านรายงาน สำรวจแหล่งอ้างอิง และ export ผลลัพธ์ได้
- ยังไม่รองรับการแก้ไขเนื้อหารายงานบนเว็บในรุ่นแรก
- Interactive Reports เน้นการอ่าน การนำทางตามหัวข้อ และการเปิดดูแหล่งอ้างอิงหรือหลักฐานที่เกี่ยวข้อง
- เหตุผล: การแก้เนื้อหาต้องจัดการประวัติการแก้ไขและความสอดคล้องระหว่างข้อความใหม่กับแหล่งอ้างอิง
- รุ่นแรกรองรับ export เป็น HTML, Markdown และ PDF ตามขอบเขตหลักฐานและ Source Explorer ด้านล่าง

### 2026-09-23 — แหล่งข้อมูลและ Search Provider

- ใช้แหล่งข้อมูลที่ค้นหาผ่าน search engine ได้เป็นค่าเริ่มต้น
- รองรับการเพิ่ม Search Provider โดยผู้ใช้ยกตัวอย่าง Tavily, arXiv และ SearXNG
- ผู้ดูแลกำหนด Search Provider ค่าเริ่มต้นได้ โดยยังไม่ได้ระบุชื่อบริการที่จะใช้ในการติดตั้งจริง
- รุ่นแรกใช้ข้อมูลจาก Search Provider เท่านั้น ยังไม่รองรับการอัปโหลด PDF หรือเอกสารส่วนตัว
- การอัปโหลดเอกสารเป็นแนวทางต่อยอด ยังไม่ได้กำหนดรุ่นที่จะรองรับ
- จากโค้ดปัจจุบัน: มี TavilySearchRM และ SearXNG ใน knowledge_storm/rm.py และมี ArxivRM ที่เรียก arXiv โดยตรงใน frontend/demo_light/arxiv_rm.py การมี adapter ยังไม่ใช่การยืนยันว่าเชื่อมต่อบริการจริงได้ในสภาพแวดล้อมที่นำไปใช้งาน

### 2026-09-23 — การจัดการ Search Provider รุ่นแรก

- ผู้ดูแลระบบเพิ่มและตั้งค่า Search Provider รวมถึง API key และ endpoint ส่วนกลาง
- ผู้ใช้เลือกจากรายการ provider ที่ผู้ดูแลเปิดให้ใช้
- รุ่นแรกยังไม่เปิดให้ผู้ใช้เพิ่ม provider หรือตั้งค่า credentials ส่วนตัว
- การเพิ่มบริการชนิดใหม่ต้องมี adapter รองรับก่อน ไม่ใช่เพียงกรอกชื่อบริการและ API key

### 2026-09-23 — จำนวน Search Provider ต่อ Run

- รุ่นแรก: ผู้ใช้เลือกหนึ่ง Search Provider ต่อ Run และเก็บข้อมูลว่า Run นั้นใช้ provider ใด
- เหตุผล: ทำให้พฤติกรรมการค้นหาและค่าใช้จ่ายเข้าใจง่ายในรุ่นแรก
- รุ่นสอง: รองรับการค้นหาผ่านหลาย Search Provider พร้อมกันภายใน Run เดียว
- รายละเอียดรุ่นสองที่ยังต้องออกแบบ: การรวมและจัดอันดับผล การตัดแหล่งข้อมูลซ้ำ งบการค้นหา และพฤติกรรมเมื่อบาง provider ล้มเหลว

### 2026-09-23 — การเลือก LLM

- ผู้ดูแลเพิ่มรายการโมเดล LLM และกำหนดว่าโมเดลใดเปิดให้ผู้ใช้เลือกได้
- ผู้ใช้เลือกตามชื่อโมเดลจากรายการที่เปิดใช้งาน ไม่ใช้โปรไฟล์ประหยัด/สมดุล/คุณภาพสูงตามข้อเสนอเดิม
- ผู้ดูแลกำหนดโมเดล default ได้
- รุ่นแรกใช้ LLM ที่เลือกหนึ่งโมเดลกับทุกขั้นตอนของ Run
- เก็บโมเดลที่เลือกไว้กับ Run เพื่อไม่ให้การเปลี่ยน default ภายหลังกระทบการเลือกโมเดลของงานเดิม
- การเลือกโมเดลแยกแต่ละขั้นตอนเป็นแนวทางต่อยอดที่ผู้ใช้สนใจ ยังไม่ได้กำหนดรุ่นที่จะรองรับ
- โค้ด STORM เดิมแยกการตั้งค่าโมเดลสำหรับการจำลองบทสนทนา การตั้งคำถาม การสร้างโครงร่าง การเขียนบทความ และการขัดเกลาบทความ

### 2026-09-23 — การทำงานเบื้องหลัง

- เมื่อเริ่ม Run แล้ว งานทำต่อเบื้องหลังแม้ผู้ใช้ปิดแท็บหรือออกจากระบบ
- ผู้ใช้กลับมาติดตามสถานะและเปิดผลลัพธ์จาก Dashboard ได้ภายหลัง
- ใช้ Worker และคิวงานแยกจากหน้าเว็บ พร้อมบันทึกสถานะ Run อย่างถาวร
- การปิดหน้าเว็บหรือออกจากระบบไม่ใช่คำสั่งยกเลิกงาน
- ข้อกำหนดให้ทำต่อจนจบไม่ได้หมายถึง retry ไม่จำกัดเมื่อเกิดข้อผิดพลาด เมื่อ Worker ล่มให้ใช้นโยบายงานถูกขัดจังหวะด้านล่าง

### 2026-09-23 — การ retry คำขอที่ล้มเหลว

- เมื่อคำขอไปยัง LLM หรือ Search Provider ล้มเหลวจากปัญหาชั่วคราว ให้ลองคำขอนั้นซ้ำอัตโนมัติไม่เกิน 2 ครั้งหลังคำขอแรก (รวมไม่เกิน 3 ครั้ง) โดยเว้นระยะเพิ่มขึ้น
- นโยบายนี้เป็นการ retry คำขอภายใน Run เดิม ไม่ใช่การเริ่มงานวิจัยทั้ง Run ใหม่
- เมื่อครบจำนวนครั้งแล้วยังไม่สำเร็จ ให้หยุดงาน แสดงสาเหตุ และเก็บผลส่วนที่ทำสำเร็จไว้
- ข้อผิดพลาดที่ลองซ้ำแล้วไม่ช่วย เช่น API key ไม่ถูกต้อง ให้หยุดทันที
- ข้อควรตรวจตอนพัฒนา: นับ retry รวมกับที่ SDK หรือ engine ทำอยู่แล้ว เพื่อไม่ให้เกิดการลองซ้ำซ้อนเกินขอบเขต
- การเก็บผลบางส่วนไม่ได้รับรองว่าสามารถ resume จากทุกจุดได้ รุ่นแรกเมื่อผู้ใช้สั่งลองใหม่จะเริ่มประมวลผลทั้งรอบ

### 2026-09-23 — การยกเลิก Run

- ผู้ใช้ยกเลิก Run ของตนเองได้ทั้งขณะอยู่ในคิวและขณะทำงาน
- งานที่ยังอยู่ในคิวยกเลิกได้ทันทีโดยไม่เริ่มประมวลผล
- งานที่เริ่มแล้วแสดงสถานะกำลังยกเลิก และหยุดเมื่อถึงจุดที่ปลอดภัย ก่อนเปลี่ยนเป็นยกเลิกแล้ว
- เก็บผลส่วนที่ทำสำเร็จไว้ การยกเลิกไม่ใช่การลบผลลัพธ์
- คำขอที่ส่งไปยังบริการภายนอกแล้วอาจยังมีค่าใช้จ่าย
- รายละเอียดจุดหยุดที่ปลอดภัยและกรณียกเลิกพร้อมกับงานเสร็จต้องกำหนดตอนออกแบบวงจรชีวิตงาน

### 2026-09-23 — จำนวน Run พร้อมกันต่อผู้ใช้

- ค่าเริ่มต้นให้ผู้ใช้แต่ละคนมี Run ที่กำลังทำงานพร้อมกันได้ 1 Run
- งานเพิ่มเติมเข้าคิวรอจนมีช่องประมวลผลว่างตามข้อจำกัดที่เกี่ยวข้อง
- ผู้ดูแลปรับจำนวน Run พร้อมกันต่อผู้ใช้ได้
- เหตุผล: ควบคุมการใช้ทรัพยากรและค่าใช้จ่าย โดยยังให้ผู้ใช้ส่งงานหัวข้อถัดไปรอไว้ได้
- จำนวน Run พร้อมกันต่อผู้ใช้ใช้ค่าเริ่มต้นส่วนกลาง โดยผู้ดูแลตั้งค่าทับ (override) เป็นรายคนได้
- งานรอสูงสุดเริ่มต้น 5 Run ต่อคน รวมงานที่รอเลือกโมเดลหรือ provider ใหม่ ผู้ดูแลปรับได้ และการส่งงานยังต้องมีโควตาเหลือพอ

### 2026-09-23 — เพดาน Run พร้อมกันทั้งระบบ

- ผู้ดูแลกำหนดเพดาน Run ที่ทำงานพร้อมกันทั้งระบบได้
- เริ่ม Run ได้เมื่อไม่เกินทั้งเพดานต่อผู้ใช้และเพดานรวมของระบบ มิฉะนั้นให้งานรอในคิว
- เหตุผล: การจำกัดต่อผู้ใช้อย่างเดียวไม่จำกัดภาระงานรวมเมื่อมีผู้ใช้จำนวนมาก
- สำหรับทดสอบ local กำหนดค่าเริ่มต้นรวมทั้งระบบ 2 Run พร้อมกัน ผู้ดูแลปรับได้ตามกำลังเครื่องและข้อจำกัดบริการ

### 2026-09-23 — การจัดสรรคิวระหว่างผู้ใช้

- เมื่อมีช่องประมวลผลว่าง ให้สลับหยิบงานระหว่างผู้ใช้ที่มีงานรอและยังไม่เต็มเพดานพร้อมกันของตน
- งานของผู้ใช้แต่ละคนเรียงตามเวลาที่ส่ง โดยหยิบงานที่ส่งก่อนก่อน
- การเริ่มงานยังต้องเคารพทั้งเพดานต่อผู้ใช้และเพดานรวมของระบบ
- เหตุผล: ผู้ใช้ที่ส่งงานจำนวนมากไม่ควรครองลำดับคิวจนผู้ใช้อื่นต้องรอครบทุกงาน
- นโยบายนี้จัดสรรโอกาสเริ่มงาน ไม่ได้รับรองเวลาเริ่มหรือเวลาเสร็จเท่ากัน เพราะแต่ละ Run ใช้เวลาต่างกัน

### 2026-09-23 — ผู้ใช้สั่งลองใหม่หลัง Run ล้มเหลว

- ปุ่มลองใหม่สร้าง Run ใหม่ใน Research Session เดิม พร้อมเชื่อมกลับไปยัง Run ที่ล้มเหลว
- คัดลอกโจทย์และค่าที่ใช้จาก Run เดิม และเก็บประวัติ ข้อผิดพลาด และผลลัพธ์ของ Run เดิมไว้
- รุ่นแรกเริ่มประมวลผลใหม่ทั้งรอบ ไม่ resume จากขั้นตอนที่ค้าง
- แยกผลลัพธ์และค่าใช้จ่ายของแต่ละ Run เพื่อให้ตรวจสอบย้อนหลังได้
- การ resume เป็นแนวทางต่อยอดหลังทดสอบการกู้คืนของ engine ยังไม่กำหนดรุ่นที่จะรองรับ
- หากค่าที่คัดลอกอ้างถึงโมเดลหรือ provider ที่ปิดใช้งาน ให้ผู้ใช้เลือกตัวที่เปิดใช้งานก่อนเริ่ม Run ใหม่ ตามนโยบายการปิดบริการด้านล่าง

### 2026-09-23 — Run ถูกขัดจังหวะเมื่อ Worker หรือเครื่องล่ม

- รุ่นแรกตรวจพบและแสดงว่า Run ที่กำลังทำถูกขัดจังหวะ พร้อมเก็บผลบางส่วนที่บันทึกไว้แล้ว
- ไม่เริ่มประมวลผลทั้งรอบใหม่อัตโนมัติ ให้รอผู้ใช้กดลองใหม่ ซึ่งสร้าง Run ใหม่ตามนโยบายเดิม
- เหตุผล: ไม่ให้เกิดค่าใช้จ่ายจากการเริ่มทั้งรอบซ้ำโดยผู้ใช้ไม่ทราบ
- งานที่ยังอยู่ในคิวและยังไม่เริ่มทำสามารถทำต่อเมื่อระบบกลับมา โดยเคารพนโยบายคิวและเพดานพร้อมกัน
- รายละเอียดทางเทคนิคในการตรวจจับ Worker ที่หายไปและป้องกันงานซ้ำยังต้องออกแบบ

### 2026-09-23 — สิทธิ์ผู้ดูแลต่อเนื้อหางานวิจัย

- ค่าเริ่มต้นผู้ดูแลเห็นเฉพาะข้อมูลจำเป็นต่อการดูแลระบบ เช่น เจ้าของงาน สถานะ โมเดล ปริมาณใช้งาน และข้อผิดพลาดที่ตัดเนื้อหาส่วนตัวออก
- หัวข้อวิจัย แหล่งข้อมูล และรายงานส่วนตัวไม่เปิดให้ผู้ดูแลอ่านโดยอัตโนมัติ
- ผู้ดูแลเข้าถึงเนื้อหางานวิจัยได้เมื่อเจ้าของอนุญาต
- เหตุผล: ให้ขอบเขต Project ส่วนตัวสอดคล้องกับสิทธิ์การเข้าถึงของผู้ดูแล

- เจ้าของระบุผู้ดูแลผู้รับสิทธิ์เป็นรายคน สิทธิ์ไม่ครอบคลุมผู้ดูแลคนอื่นโดยอัตโนมัติ

### 2026-09-23 — การส่งรายงานให้ผู้อื่น

- ขอบเขตนี้ไม่เปลี่ยนสิทธิ์ช่วยตรวจปัญหาที่เจ้าของให้ผู้ดูแลเป็นรายคน

### 2026-09-23 — รูปแบบไฟล์ export รุ่นแรก

- รองรับ HTML, Markdown และ PDF ตั้งแต่รุ่นแรก
- ค่าเริ่มต้น export รายงานพร้อม citation และรายการอ้างอิง

- ระบุชัดว่าข้อความหลักฐานเป็นข้อความบางส่วน ไม่ใช่ต้นฉบับเต็ม
- HTML เป็นไฟล์ที่เปิดอ่านได้ด้วยตัวเอง โดยไม่ต้องล็อกอินหรือเชื่อมต่อระบบ
- HTML มีสารบัญ ลิงก์ citation ภายใน และเปิดดูข้อความหลักฐานได้เมื่อผู้ใช้เลือกแนบหลักฐานตอน export
- การอ่านรายงานและหลักฐานที่แนบทำได้แบบออฟไลน์ ส่วนการเปิดเว็บไซต์ต้นทางยังต้องใช้อินเทอร์เน็ต

### 2026-09-23 — ขอบเขต Source Explorer

- แสดงเฉพาะแหล่งข้อมูลที่ถูกอ้างอิงในรายงานที่ผู้ใช้กำลังดู
- ไม่แสดงกลุ่มแหล่งที่ค้นพบแต่ไม่ได้ถูกอ้างอิงในรายงาน
- ข้อนี้กำหนดขอบเขตการแสดงผล ไม่ได้กำหนดให้ลบข้อมูลการค้นหาดิบที่ engine เก็บไว้
- เมื่อคลิก citation ให้เปิดแผงแหล่งอ้างอิงด้านข้างรายงานโดยไม่เปลี่ยนหน้า
- แผงแสดงชื่อแหล่งข้อมูล ลิงก์ต้นทาง และข้อความหลักฐานที่บันทึกไว้ พร้อมปุ่มเปิดเว็บไซต์ต้นทาง
- เหตุผล: ผู้ใช้สามารถอ่านรายงานเทียบกับหลักฐานได้ต่อเนื่อง

### 2026-09-23 — การเข้าร่วมระบบรุ่นแรก

- ผู้ดูแลสร้างบัญชีให้ผู้ใช้ รุ่นแรกไม่เปิดให้คนทั่วไปสมัครเอง ส่วนการเชิญทางอีเมลอยู่ในรุ่นสอง
- เหตุผล: ระบบใช้ API key ส่วนกลางที่มีค่าใช้จ่าย จึงควบคุมผู้มีสิทธิ์ใช้งานตั้งแต่เริ่ม
- การเปิดสมัครสาธารณะเป็นแนวทางต่อยอดหลังมีโควตาและนโยบายการใช้งาน ยังไม่กำหนดรุ่นที่จะรองรับ
- รุ่นแรกเข้าสู่ระบบด้วยอีเมลและรหัสผ่าน ยังไม่รวมการเข้าสู่ระบบผ่าน Google หรือบัญชีองค์กร
- รุ่นแรกผู้ดูแลกดรีเซ็ตรหัสผ่านให้ผู้ใช้ และบังคับผู้ใช้ตั้งรหัสผ่านใหม่ก่อนเข้าใช้งานตามปกติ
- รุ่นสองเพิ่มอีเมลเชิญตั้งรหัสผ่านและอีเมลรีเซ็ตรหัสผ่าน รุ่นแรกไม่ต้องมีระบบส่งอีเมลสำหรับขั้นตอนเหล่านี้
- ทั้งการสร้างบัญชีและการรีเซ็ตใช้ลิงก์ตั้งรหัสผ่านที่ระบบสร้าง ใช้ครั้งเดียว และมีวันหมดอายุ
- ผู้ดูแลคัดลอกลิงก์ส่งให้ผู้ใช้เอง ผู้ใช้เปิดลิงก์เพื่อตั้งรหัสผ่านของตน โดยผู้ดูแลไม่ต้องทราบรหัสผ่าน
- ลิงก์ตั้งรหัสผ่านครั้งแรกและลิงก์รีเซ็ตมีอายุ 24 ชั่วโมงนับจากออกลิงก์ และใช้ได้ครั้งเดียว
- เมื่อผู้ดูแลออกลิงก์ใหม่ ลิงก์เดิมใช้ไม่ได้ทันที เพื่อให้มีลิงก์ที่ใช้งานได้เพียงหนึ่งรายการต่อบัญชี

### 2026-09-23 — โควตา Run รายเดือน

- กำหนดโควตาจำนวน Run รายเดือนต่อผู้ใช้ โดยผู้ดูแลปรับเป็นรายคนได้
- โควตารายเดือนใช้ค่าเริ่มต้นส่วนกลาง และผู้ดูแลตั้งค่าทับ (override) เป็นรายคนได้ ผู้ใช้ที่ไม่มีค่ารายบุคคลใช้ค่าเริ่มต้นส่วนกลาง
- เหตุผล: เพดานงานพร้อมกันควบคุมภาระงานในขณะหนึ่ง ส่วนโควตารายเดือนควบคุมจำนวนการใช้งานสะสม
- เมื่อส่งงานเข้าคิวให้จองโควตาไว้ เพื่อไม่ให้ส่งงานเกินโควตาที่เหลือ หากยกเลิกก่อนเริ่มให้คืนโควตา
- เมื่อเริ่มประมวลผลให้นับ 1 Run แม้ผู้ใช้ยกเลิกภายหลัง เพราะอาจมีค่าใช้จ่ายแล้ว
- หากล้มเหลวจากระบบหรือบริการภายนอกให้คืนโควตา แต่ยังบันทึกค่าใช้จ่ายที่เกิดขึ้นจริง
- การจอง นับ และคืนโควตาทำอัตโนมัติเบื้องหลัง ผู้ใช้ไม่ต้องจัดการเอง
- ผู้ใช้เห็นยอดที่ใช้แล้ว ยอดที่จองสำหรับงานในคิว และยอดคงเหลือ พร้อมข้อความเมื่อโควตาเต็มหรือได้รับคืน
- เริ่มรอบโควตาใหม่วันที่ 1 ของทุกเดือน เวลา 00:00 ตามเขตเวลา Asia/Bangkok โดยไม่ทบยอดที่เหลือ
- งานที่เข้าคิวหรือกำลังทำข้ามเดือนยังนับกับเดือนที่จองไว้ตั้งแต่แรก ไม่หักโควตาเดือนใหม่ซ้ำ
- การคืนโควตาของงานข้ามเดือนปรับยอดในเดือนที่จองไว้ ไม่เพิ่มสิทธิ์ให้เดือนใหม่
- สำหรับทดสอบ local กำหนดโควตาเริ่มต้น 10 Run ต่อคนต่อเดือน ผู้ดูแลปรับได้

### 2026-09-23 — ข้อมูลจากระบบทดสอบเดิม

- เว็บใหม่เริ่มด้วยข้อมูลใหม่ได้ ไม่ต้องย้ายบัญชี รายงาน หรือประวัติจากระบบ Streamlit เดิม
- เหตุผล: ข้อมูลเดิมเป็นข้อมูลทดสอบที่ผู้ใช้ไม่ต้องการเก็บต่อ
- ไม่ต้องพัฒนากระบวนการนำเข้าข้อมูลเก่าสำหรับการเปิดตัวรุ่นแรก
- การตัดสินใจนี้ไม่เปลี่ยนขอบเขตการใช้ STORM engine และ logic เดิมที่นำกลับมาใช้ได้
- บันทึกนี้เป็นข้อกำหนดการย้ายระบบ ยังไม่มีการลบข้อมูลจริงในขั้นออกแบบ

### 2026-09-23 — การติดตั้งและการเข้าถึง

- ผู้ใช้ต้องล็อกอินเพื่อเข้าใช้งานเว็บ
- ส่วนประกอบของแอปทั้งหมดติดตั้งและรันเองผ่าน Docker รวมเว็บ Application Backend, Worker/ระบบคิว, PostgreSQL, ระบบบัญชี และที่เก็บไฟล์
- ไม่พึ่งบริการฐานข้อมูล ระบบบัญชี หรือที่เก็บไฟล์แบบ hosted สำหรับการทำงานหลักของแอป
- เก็บข้อมูลถาวรแยกจากวงจรชีวิต container โดยใช้ persistent volume
- LLM และ Search Provider เรียกผ่าน API ตามเดิม ไม่จำเป็นต้องรันบริการเหล่านี้เองใน Docker
- รุ่นแรกใช้งานและทดสอบบน local โดยยังต้องล็อกอินตามข้อกำหนดเดิม
- ย้ายการเปิดเข้าถึงผ่านโดเมน/อินเทอร์เน็ตไปเป็นรุ่นสอง หลังทดสอบการทำงานบน local ผ่านครบ ขอบเขตการติดตั้งภายนอกและ HTTPS จะออกแบบในรุ่นนั้น
- รุ่นแรกติดตั้งบนเครื่องเดียวด้วย Docker Compose โดยแยก container ตามหน้าที่และใช้ persistent volume
- เหตุผล: ให้ติดตั้งและดูแลง่ายก่อน การกระจาย Worker หลายเครื่องเป็นแนวทางต่อยอดเมื่อปริมาณงานต้องการ
- ระบบปฏิบัติการและทรัพยากรของเครื่องจริงยังไม่ได้กำหนด

### 2026-09-23 — หน้าตั้งค่าบริการภายนอก

- ผู้ดูแลตั้งค่า LLM และ Search Provider ผ่านหน้า frontend สำหรับผู้ดูแล
- ครอบคลุมรายการโมเดล/บริการ API key, endpoint และการเปิดให้ผู้ใช้เลือกตามขอบเขตที่ตกลงไว้
- ผู้ดูแลกำหนด default ได้ทั้ง LLM และ Search Provider
- หน้าเริ่มวิจัยเลือก Search Provider default ไว้ให้ ผู้ใช้เปลี่ยนเป็นตัวอื่นจากรายการที่เปิดใช้งานได้ก่อนส่ง Run
- การเปลี่ยน default ไม่เปลี่ยน provider ที่บันทึกไว้กับ Run เดิม
- แนวทางทางเทคนิค: frontend เป็นหน้าจอจัดการค่า ส่วน Backend ตรวจสิทธิ์ จัดเก็บ credentials และส่งคำขอไปยังบริการผ่าน Worker/engine โดยไม่ส่ง key ที่บันทึกไว้ให้ผู้ใช้ทั่วไปหรือเก็บในไฟล์ export

### 2026-09-23 — การปิดใช้งานโมเดลหรือ Search Provider

- งานใหม่เลือกโมเดลหรือ provider ที่ผู้ดูแลปิดใช้งานแล้วไม่ได้
- งานที่ยังอยู่ในคิวและเลือกตัวที่ถูกปิดให้หยุดรอผู้ใช้เลือกตัวใหม่ ไม่เปลี่ยนให้โดยอัตโนมัติ
- งานที่กำลังประมวลผลใช้ค่าเดิมต่อจนจบ หากบริการยังใช้งานได้
- การปิดรับงานใหม่ไม่ใช่คำสั่งยกเลิก Run ที่กำลังทำ
- หากบริการใช้งานไม่ได้ ให้ใช้กติกาข้อผิดพลาดและ retry ที่ตกลงไว้
- ระหว่างรอผู้ใช้เลือกตัวใหม่ ให้เก็บการจองโควตาเดิมไว้จนผู้ใช้แก้ไขหรือยกเลิก โดยข้ามงานนี้ให้คิวอื่นเดินต่อ
- เมื่อเลือกตัวใหม่ ให้ต่อท้ายคิวของผู้ใช้โดยใช้ Run เดิมเพราะยังไม่เริ่มประมวลผล และไม่จองหรือหักโควตาซ้ำ
- หากผู้ใช้ยกเลิก ให้คืนโควตาตามกติกางานที่ยังไม่เริ่ม โดยอ้างอิงเดือนที่จองไว้เดิม

### 2026-09-23 — การสร้างผู้ดูแลคนแรก

- เมื่อติดตั้งระบบใหม่ ให้สร้าง Admin คนแรกผ่านหน้าตั้งค่าครั้งแรก
- ต้องใช้รหัสตั้งต้นที่ผู้ติดตั้งกำหนดและส่งให้ระบบผ่าน Docker secret
- เมื่อสร้างบัญชีสำเร็จให้ปิดขั้นตอนตั้งค่าครั้งแรก โดยการ restart container ไม่เปิดขั้นตอนนี้ใหม่
- ไม่ใช้บัญชีหรือรหัสผ่านเริ่มต้นร่วมกันทุกการติดตั้ง

### 2026-09-23 — ถังขยะและการลบข้อมูล

- รายละเอียดการกู้คืนรายการย่อยและข้อมูลที่อยู่ในชุดสำรองต้องกำหนดเพิ่มเติม

### 2026-09-23 — การสำรองข้อมูลอัตโนมัติ

- เก็บภาษารายงานไว้กับแต่ละ Run การเปลี่ยนภาษาหน้าจอไม่เปลี่ยนภาษาของรายงานที่สร้างไว้แล้ว

## เกณฑ์รับงานรุ่นแรกที่ยืนยันแล้ว

สถานะ: เป็นเกณฑ์สำหรับตรวจรับระหว่างพัฒนา ยังไม่ได้ดำเนินการทดสอบเว็บใหม่หรือยืนยันว่าผ่าน

- [ ] ติดตั้งบน local ด้วย Docker Compose ใหม่ สร้าง Admin คนแรก และสร้างบัญชีผู้ใช้พร้อมตั้งรหัสผ่านได้
- [ ] ผู้ดูแลตั้งค่า LLM และ Search Provider ผ่านเว็บ แล้วผู้ใช้สร้างรายงานจริงได้ทั้งภาษาไทยและอังกฤษ
- [ ] คิวทำงานตามเพดานและการสลับผู้ใช้ รวมถึงกรณีรอเลือกโมเดลหรือ provider ใหม่
- [ ] โควตาจอง นับ คืน และเปลี่ยนรอบเดือนตามกติกา รวมถึงงานข้ามเดือน
- [ ] ยกเลิกงานในคิวและงานที่กำลังทำได้ตามกติกา และกดลองใหม่แล้วสร้าง Run ใหม่ที่เชื่อมกับรอบเดิม
- [ ] ปิดหน้าเว็บแล้วงานทำต่อ และกลับมาดูสถานะกับผลลัพธ์ได้
- [ ] จำลอง Worker ล่มแล้วระบบตรวจพบ Run ที่ถูกขัดจังหวะ เก็บผลที่บันทึกไว้ และรอผู้ใช้ลองใหม่ โดยไม่เริ่มทั้งรอบอัตโนมัติ
- [ ] ผู้ใช้เข้าถึงข้อมูลของผู้อื่นไม่ได้ ผู้ดูแลอ่านเนื้อหาได้เฉพาะสิทธิ์ที่เจ้าของให้ และสิทธิ์หมดอายุหรือเพิกถอนแล้วใช้ต่อไม่ได้
- [ ] คลิก citation แล้วอ่านหลักฐานของแหล่งที่ถูกอ้างอิงจากแผงด้านข้างได้
- [ ] export HTML, Markdown และ PDF ได้ตามตัวเลือกแนบหลักฐาน โดย HTML เปิดอ่านออฟไลน์ได้ตามขอบเขตที่กำหนด
- [ ] ลบแล้วเข้าถังขยะ กู้คืนภายใน 30 วันได้ และจัดการงานที่เกี่ยวข้องก่อนลบไฟล์ถาวร

ใช้ชุดนี้เป็นเกณฑ์รับงานรุ่นแรกก่อนขยับไปรุ่นสอง

## ประเด็นที่ยังไม่ได้ตัดสินใจ

- ระบบปฏิบัติการและทรัพยากรเครื่องทดสอบ local
- รายละเอียดทางเทคนิคสำหรับพัฒนา เช่น framework, schema, API, กลไกคิว และรูปแบบข้อมูลรายงาน/หลักฐาน ยังต้องออกแบบจากขอบเขตที่ยืนยันแล้ว

ข้อเสนออื่นจากการสนทนายังไม่ถือเป็นข้อสรุป จนกว่าจะได้รับการยืนยัน
